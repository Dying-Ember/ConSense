## 建议与当前结论

比赛审查模型按约 120B 的 MoE 规划。优先验证 GPT-OSS-120B 官方 MXFP4；Qwen3.5-122B-A10B 的量化版本作为质量对照。4B、7B、Bonsai 与 27B 对照结果不能定义最终比赛算力基准。

现有 `vetting-h800` 测试 profile 采用 131,072 token 总上下文，预留 16,384 输出和 16,384 安全余量，完整输入门限为 98,304 token。131,072 来自候选 GPT-OSS-120B 的原生上下文规格，并非由 H800 80 GB 显存反推的最大容量；输出和安全余量均为临时工程选值，尚未通过实际输出分布及目标 tokenizer 偏差校准。完整输入计数已经包含指令、证据、JSON schema 和消息封装，安全余量不是再次扣除提示词长度。

该 profile 用于保留一个可比实验条件，不能据此认定所有比赛候选或 API 对照均只能使用 128K。Qwen3.5-122B-A10B 官方原生上下文为 262,144 token。各候选应分别记录原生支持范围、量化权重和推理引擎，再校核实际可用显存与完整输入；128K 和 256K 的结果必须标明各自预算身份。当前未完成 H800 容量实测，没有证据证明更大上下文装不下。

Qwen 官方还提供通过 YaRN 扩展至 1,010,000 token 的配置，但这也不是单张 H800 的部署验收。是否能运行更大窗口，要同时满足模型支持范围和实际显存预算：驻留权重 + KV cache／线性状态 + 推理工作区及预填充峰值 + 审查阶段仍常驻的辅助模型 + 设备余量。若辅助模型串行卸载，必须观测实际释放后再计入审查阶段预算；不能既假定卸载又把相关模型视为随时可调用。

| 项目 | 本次方案 |
| --- | --- |
| 比赛资源 | 1 × H800 80 GB；27 vCPU；250 GB RAM；650 GB 高性能存储 + 1,250 GB 普通存储 |
| 主候选 | GPT-OSS-120B MXFP4，单请求审查，BF16 KV cache；H800 上的实际吞吐与峰值尚未验证 |
| 证据原则 | 先保全解析及原生表格，再按相关引用组成完整组；仅完整输入计数决定是否可送审 |
| 用户检查 | 提供切片／向量条目、逐页 OCR、任务召回与 rerank 前后及最终送审材料的检查界面 |

### 效果判断边界

已经确认并修复的基础问题包括长文本窗口静默截断及原生表格传递不完整。本轮还修正旧字符门控和相关引用分包。当前没有新的完整模型审查质量结果，因此不能声称漏报率、准确率或综合效果已经达到比赛要求。

代码测试、向量写入与探针留证用于证明流程行为；端到端质量必须由固定评价集、真实模型输出及人工核对证明。

## 1  模型与显存预算

| 候选 | 已核事实 | 部署判断 |
| --- | --- | --- |
| GPT-OSS-120B | 117B 总参数、约 5.1B 激活；原生 131,072 上下文；官方 MXFP4 原始权重索引 65,248,815,744 字节，约 60.768 GiB | 首选验证候选。官方可单 H100 运行；这不等于本项目已在 H800、128K 总窗口下实测通过；输入与输出合计必须在该窗口内 |
| Qwen3.5-122B-A10B | 原生 262,144 token；48 层：12 全注意力 + 36 线性注意力；128K／256K BF16 全注意力 KV 分别约 3／6 GiB，另有线性注意力状态；官方 BF16 权重约 232.99 GiB | 单张 80 GB 需要可用量化权重与兼容内核。第三方 Q4 必须验证格式、质量及长上下文，不能只凭激活参数判断可装载；尚未证明 256K 不可部署 |
| 27B／32B 对照 | 可用于预算、吞吐或质量对照 | 保留实验记录；不作为默认比赛审查模型 |

### GPT-OSS 的 KV cache 推导

配置为 36 层，其中 18 层全注意力、18 层滑动窗口注意力；8 个 KV heads、head dimension 64、BF16 每元素 2 字节。按每个 token 的 K 与 V 计算：2 × KV heads × head dimension × dtype bytes × 注意力层数。

128K、单序列、滑动窗口 128 正确保留时，KV 理论值约 4.505 GiB。若运行时为全部 36 层保留全长 KV，上界约 9 GiB。运行时的块对齐、工作区、CUDA graph、前缀缓存和并发都会增加占用，不能把理论 KV 当成最终峰值。

| 显存项 | 128K 串行规划 |
| --- | --- |
| 全部专家权重 | 官方原始索引约 60.768 GiB；存储字节与运行时驻留仍需区别 |
| BF16 KV cache | 滑窗正确保留约 4.504 GiB；全层全长保守上界 9 GiB |
| 工作区与设备余量 | 分别预留 6 GiB 和 4 GiB；均为规划假设，需实测核对 |
| 审查阶段辅助模型 | 正式 OER 模型统一 CUDA；按阶段卸载自有模型并观测实际释放，共驻另按峰值准入 |
| 合计与硬件验收 | 滑窗规划约 75.272 GiB；全层全长约 79.768 GiB，余量很紧。以实际 GPU 可用字节和峰值验收 |

GiB = 2^30 字节；80 GB 的产品标签不直接替代实际 device.total_memory。128K 是 GPT-OSS 候选测试档，尚未 H800 压测，不代表硬件通用上限。16K token 安全余量与上述 4 GiB 显存余量是两项不同的预算。GPT-OSS 的 256K KV 算术值不代表其原生支持 256K；Qwen 的 256K 原生支持也不代表某个量化版本已在 H800 上运行通过。

补充实际计数：生产 Q6 全局输入的 MiniMax 计数为 108,855，按现有 98,304 门限被标记为 `over_budget`，但 108,855 + 16,384 = 125,239，仍低于 131,072；因此该结果只证明超过了含额外 16K 余量的测试政策，不能称为模型或 H800 无法容纳。关联完整证据组的独立计数为 13,728，可通过当前政策。两次均为供应商输入估计、没有生成调用；这些数字不能冒称目标模型 tokenizer 精确计数或硬件容量验证。

## 2  数据与检索流程

| 步骤 | 实现方式 | 检查重点 |
| --- | --- | --- |
| 原件与解析 | 逐文件保存 source hash、解析状态、页／块／字符位置；原生 PDF 文本优先，扫描页走 OCR | OCR 误识别、漏页、阅读顺序、空白页与表格重构分开记录；无法确认的页标 needs_review |
| 切片与窗口 | 语义父切片保留完整原文、表格行／单元格、条款所属与来源；模型输入窗口按 tokenizer 拆分 | 当前 embedding 和 rerank 窗口上限 512 token、重叠 64；原父文本不因此裁短 |
| 向量与词项召回 | 保留 BAAI/bge-m3 与独立 BM25 召回；保存 dense、BM25、RRF 排序与来源 | 固定与现场材料都走同一通用协议；签名绑定模型、分词器、数据和窗口配方 |
| 重排序 | BAAI/bge-reranker-v2-m3 对候选窗口打分；按已记录聚合策略回到完整父切片 | 每个任务可见 query、前后 rank／score、窗口、入选或排除原因，不能只看最终 topK |
| 证据排包 | 相关原始来源及其已识别引用优先同组；完整组超过预算时才在完整请求边界拆分 | 分包、缺失引用、未知来源、超预算和计数失败分别显示；单包可读不等于联合比较完整 |

### 固定资料与现场变动资料

NTT、SCT、SCC 模板以及 GCT、GCC、SL 可离线预解析、预切片、预嵌入后随包上传。现场其他文件不同，必须从原件重新解析、切片、嵌入与查询；不得依赖当前文件名、内容答案或评价集目标字符串。

标准包应包含权重／分词器版本、原件与切片 hash、索引签名、解析及 OCR 质量标记、重建脚本和验证记录。现场检查签名一致性；实际 Linux／H800 导入与检索仍需要赛前演练。

### 已经有的数据证据

当前 44 份材料的 native-v3 索引包含 13,464 个父切片和 13,602 个窗口；独立读取核对了索引载荷、范围与向量。13 个标准资料页面仍需人工复核。这个索引版本尚无新的完整检索评价运行，因此旧版本任务结果必须单独标识。

## 3  前端检查界面与审查 harness

| 页面 | 应显示的真实信息 | 验收方式 |
| --- | --- | --- |
| 切片与向量库 | 数据集／索引版本；文件、角色、页或条款；父切片全文；原生表格；embedding 窗口、维度与来源 | 从文件定位到切片，再定位到向量窗口；可分页、搜索、查看全文和原件；live 与 saved 快照分开标识 |
| OCR 逐页检查 | 页号、提取来源、文字、质量状态；对应原件入口；可用时显示页面图像／框 | 抽查扫描页、表格页、数字、否定词、页脚；缺少页面图像或人工校对就明确显示缺失 |
| 任务召回与 rerank | 真实 query；dense／BM25／RRF／rerank 候选；前后 rank／score；最终选取与送审材料 | 检查重要条件是否被召回、被降序、被 topK 或排包挡住；旧任务不冒称新索引结果 |

### harness 的职责

采用可观察的状态流程：来源冻结 → 检索 → 重排序 → 关联证据组 → 完整输入计数 → 模型调用 → 输出解析 → 引用与来源校验 → 人工复核 → 导出。每个阶段保存输入身份、参数、输出、耗时和明确状态。

输入门控读取完整消息及 schema；当前临时 GPT-OSS 候选政策以 98,304 token 为输入边界，超出则完整分包。该数不是 H800 的通用容量上限。计数未知、网络失败、材料不完整和模型空结果分开记录。计数结果只是预算估计；供应商 token 与最终模型 tokenizer 的差异需要单独校核。

单包结果只能引用该包实际提供的来源。跨包归并通过明确的引用与来源身份校验，不能把某条款在不同包分别出现解释成模型已做过联合比较。

### 是否需要 agent runtime

先保留自研的有界调度与明确状态机，避免框架替换掩盖数据问题。只有在证据齐全、输入预算正确、输出校验通过后，仍出现可重复的规划或多轮取证失败，才比较工具循环或开源 agent runtime。模型能力、提示词和工作流的对照应使用同一材料、预算与评价集。

### 接下来的三次可交付验收

第一步：用户能打开检查页，核对真实切片、OCR 页和任务 rerank。补齐发现的数据错误并记录具体文件／页／切片。

第二步：用相同材料、明确标识的候选窗口与输入政策重跑排包及输入计数。现有 128K 档保留为对照；Qwen 的原生 256K 应独立核算，不能被 GPT-OSS 的窗口假设排除。逐请求核对旧门控阻挡是否解除、必要条件是否同包、超预算或未知是否公开显示；旧结果与新结果分别留存。

第三步：在证据验收后用 MiniMax 完成审查对照，按人工标注评价召回与漏报、误报、引用正确率、条件完整性、无效输出率和端到端耗时。比赛模型到位后在相同基准上复验。

每次实验固定材料与模型／索引身份，记录参数、提示词、完整输入、各阶段候选及分数、原始输出与失败。优先改变一个关键变量；评价标签只用于验收，不进入生产召回或证据排序。

## 2026-10-09：单 H800 的混合解析与模型切换成本

状态：工程设计建议，未部署该调度器、未运行融合对照、未测试 H800 的真实加载时间。用户已确认总预算一张 80GB 卡、模型可卸载／加载；赛方实际约 120B MoE 的名称、量化、推理引擎和初始部署方式仍未确认。不能把前文的候选模型当已选定模型，也不能依赖比赛外部推理算力。本机 MiniMax 继续用于开发对照，不作为比赛资源假设。

用户随后强调主机内存和高速存储已完整提供。资源按 **250GB RAM、650GB 高性能存储、1250GB普通存储、27vCPU、1×H800 80GB** 作为明确规划输入，不重复请求这些配置。以约60–70GB量化LLM权重的候选量级规划，**默认建设RAM兼容权重热缓存**，使LLM释放VRAM后不需要每个正常批次从磁盘冷读。选择能保持量化表示、避免临时展开完整精度大副本的加载路径；真实引擎确定后验证缓存与host峰值。高速存储用于模型文件、当前批次及活跃索引；普通存储用于原件及历史raw／assets归档，产物descriptor与SHA继续可回取。磁盘容量已足，实际持续带宽和加载实现分别测量；容量不当作吞吐结果。

### 混合方式与质量收益来源

混合发生在原生证据、两套完整解析候选和来源结构之间；模型同时常驻不是质量融合的必要条件。规则沿用 Q1／Q8／Q10：

1. DOCX 保留 POI／OOXML，可靠可见 PDF 文字保留原生字符／坐标／表单表示；扫描及隐藏旧 OCR 层覆盖的扫描区域运行 Paddle 与 MinerU 两套完整解析。原件、两路早期结果、JSON、assets、配方及失败分别保存。
2. 将 native／Paddle／MinerU 对齐到同一原物理页坐标，处理 CropBox、全页及局部旋转；多对多 block 对齐后每路各自构建完整条款／表格组，保留父子、续行、表头、cell/span、注释和图像归属。
3. 使用实际原件支持的结构检查与文件级评价选择候选。列线／表头／空状态框／编号连续性／文字覆盖用于发现问题，不能单凭它们或 confidence 证明正确。整表组采用同一候选，不逐格拼接两家的值；选用结果记录 source、parser、group、原始 pointer、验证与 adopted reason。
4. 本轮原始 PDF 实测支持 Paddle 在 GCT 编号、APB 漏块和 Appendix H 五列空表上的候选优势，MinerU 在 SL AMR 三页状态表上的候选优势。新增文件按可泛化结构特征和参考评价判断，不能写成固定页号或样板答案规则。FoT 删除状态、APL 空槽、APU 前缀等共同缺陷须独立从原件恢复或标局部 unknown，双路一致不能补成真值。
5. LLM 可在证据充分的分歧包上提出字符／关系修复候选；接受结果仍须有可定位原件证据，数值、否定、单位、编号、有效／删除状态不得凭语言流畅度更改。尚未确认赛方 LLM 有视觉能力，不能预设它能读裁图。首版图像按 Q10=A 返回完整正确原图／表组，不新增箭头语义推断。
6. 只将带来源和真实 quality 的 canonical 投影送入长结构／短窗口索引。两家版本不重复成为两条合约事实；unknown 限制依赖它的判断，保留可靠部分。

质量依据为 [原始 PDF 实测](./testing/original-pdf-dual-parser-bf16-validation-20261009.md)，23 风险页／14 原件／37 关键检查及每路四页 FP32 控制。该实验没有跑融合产线或新文件留出，混合改善是可验证的工程假设。

### 按整批文件分阶段调度

一次导入批次的推荐顺序如下，已采纳的扫描全面双解析不减少为仅风险二次识别：

| 阶段 | GPU 工作 | RAM／磁盘保存与切换条件 |
| --- | --- | --- |
| 0 原生准备 | 可在 CPU 先识别范围／身份、抽原生结构、渲染 | 已校验固定来源复用；新增来源按真实 revision 处理，形成整批任务 |
| 1 让出 LLM GPU | 等本机受控推理请求完成后让 LLM 休眠／卸载 | 保留引擎支持的 RAM 权重副本或本地权重文件、对话消息和配置；观测真实释放，不把 empty_cache 当卸载 |
| 2 Paddle | 保持一套 BF16 mixed 模型，跑完整批次 | 每文档保存全部产物；正常批次不每页切模型；完成退出／释放后再交 GPU |
| 3 MinerU | 保持一套 BF16 完整模型，跑完整批次 | 保存完整第二路产物／失败，之后释放；两套 parser 顺序运行 |
| 4 融合／建索引／审查取证 | 融合和门控主要在 CPU；embedding、已知审查 queries 的 rerank 统一 CUDA 分阶段批处理 | 候选和 canonical、向量、query-bound 排序均带版本；分数不成为新 query 的通用缓存事实 |
| 5 LLM 审查／咨询 | 恢复大 LLM，复验模型 ready 及请求预算 | 一批正常流程只需恢复一次 LLM；源关系确认后生成，checkpoint/engine/tokenizer/KV身份保存 |

表中的一次恢复是正常批次目标，失败恢复或新导入是新的调度事件。用户对话与业务状态存储在 RAM／数据库／磁盘中；GPU KV 释放后需要重新 prefill，不能把过去的对话当丢弃或默认为仍有 prefix cache。

2026-10-10 用户最新指示覆盖先前的 CPU 备选：Advisory 的 query embedding／rerank 也统一 CUDA。连续问答优先保持大 LLM 热驻留，辅助模型共驻须证明最大请求峰值和设备余量；不能准入时排队或按受控 GPU 阶段切换，不静默走 CPU。新文档导入合并成批次进入 GPU 任务队列，前端区分处理资料／恢复模型／正在生成，仍计入权重加载和重新 prefill 的成本。

固定资料可在允许条件下赛前精修、解析、嵌入及绑定版本缓存；比赛新增资料仍需要上述真实处理。只复用与源 SHA／scope／模型／配方一致的产物，不能借缓存掩盖未完成的双路解析或共同错误。

### 权重读入 VRAM 的成本

实际要迁移的字节数由选定权重、量化和引擎表示决定。约 120B 总参数的纯 payload 算术为 BF16 240GB、INT8 120GB、4bit 60GB，均使用十进制 GB，未计量化 scale、非量化参数或临时表示。MoE 的激活参数少减少计算量，不能据此只存激活专家。单卡是否满足权重＋KV／状态＋工作区＋预填充峰值＋辅助模型＋设备余量，须读取实际 device.total_memory 和峰值；总预算 80GB 不等于有 80GB 空闲供 OER。

若 CPU／RAM 中已有兼容的完整权重副本，可直接释放 GPU 权重、之后回迁该副本，不必每次先把相同权重从 GPU 回拷到 RAM。只有没有可用副本且必须保留 GPU 权重内容时才增加 D2H。引擎是否支持量化权重的 sleep／wake 或 offload、是否保留执行图及哪些缓存，需要单独验证；不能将通用 `.to('cpu')` 假定为所有量化引擎都可用。

以下只是带宽算术场景，**不是 H800 实测时间**。假设实际 RAM→GPU 迁移 W=60GB（60×10^9 bytes），有效 host/device 带宽 B：

| 假设有效 B | W/B 的纯传输理论下界 |
| --- | ---: |
| 8GB/s | 7.5 秒 |
| 12GB/s | 5 秒 |
| 16GB/s | 3.75 秒 |
| 24GB/s | 2.5 秒 |

这里要测 host→device 通道，不能拿 H800 的 HBM 内部带宽做除数。实际 warm ready 时间还可能包含张量分配、量化重排、内核／CUDA graph 恢复；首次回答另有 tokenizer／prefill／decode 和 TTFT。小 parser 本机模型加载约 Paddle 4.169 秒／MinerU 1.673 秒来自 A4000 实验，包含当时加载路径，未控制冷／暖缓存，不能推为 H800 或大 LLM 的加载时间。

冷加载还涉及磁盘／网络权重读取、反序列化和 CPU 临时张量。假设实际需读 60GB、磁盘有效读取 3GB/s，仅磁盘步骤下界就是 20 秒；这也是场景算术。支持流水读取／GPU拷贝重叠时不能一律把 disk 与 H2D 时间相加，应分别保存分段与整体时长。已在 OS page cache 中的 mmap 不等同于 RAM 内已有引擎可直接回迁的权重对象。

250GB RAM 为约 60GB 量化权重缓存提供算术空间，但还要纳入反序列化临时副本、框架 allocator、pinned memory、文件 page cache、OER 产物和索引、其他进程的 host 峰值。只允许在这些预算有余量时预取／保留副本；不能承诺完整系统仅需一份 60GB 内存。

### 必须新增的验证

- **混合质量对照**：同源、同参考、同两路原始候选，比较固定 Paddle 输出与完整组混合投影；逐项核对条款、表格、编辑状态、遗漏、来源／资产回取，另做真正新文件留出。当前 37 关键点不能冒充全文gold。
- **冷／暖加载对照**：选定真实120B权重／引擎后，保存下载／权重读取、host ready、H2D、GPU ready、kernel warm、首次prefill／TTFT、实际VRAM释放与host峰值；缓存状态／量化／ctx／并发明确标识。重复测试报告中位数和尾部时延，单次启动日志不称稳定性能。
- **整批切换对照**：完整批次测试暂停／排队／两路解析／融合／索引／LLM恢复；一次正常批次的LLM重载次数及用户可见等待单独记录。错误和中途取消保存checkpoint，恢复不覆盖旧产物。
- **容量准入**：阶段最大输入、表组面积／token、batch、ctx及并发绑定 profile，以真实峰值和余量准入。分别观测allocated／reserved／整卡／host，不相加、不用瞬时free推断并发安全；资源不足排队、缩小已验证 batch 或按阶段卸载／恢复自有模型，无法准入时明确报错。正式 OER 不转为 CPU 配方，不静默降分辨率／截断。

当前证据接口已有两路原始产物保全与候选结构投影，可复用；真实坐标变换、多块／跨页完整组、共享缺页终态、规范采用投影和artifact回取仍需实现。现有 `oer_server` 明确拒绝把候选bundle当canonical事实，必须保持这一契约。此补充仅更新设计文档，未切换在线服务、重新加载Bonsai或部署H800。
