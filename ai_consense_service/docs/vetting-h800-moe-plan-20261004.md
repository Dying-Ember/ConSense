## 建议与当前结论

比赛审查模型按约 120B 的 MoE 规划。优先验证 GPT-OSS-120B 官方 MXFP4；Qwen3.5-122B-A10B 的量化版本作为质量对照。4B、7B、Bonsai 与 27B 对照结果不能定义最终比赛算力基准。

现有 `vetting-h800` 测试 profile 采用 131,072 token 总上下文，预留 16,384 输出和 16,384 安全余量，完整输入门限为 98,304 token。131,072 来自候选 GPT-OSS-120B 的原生上下文规格，并非由 H800 80 GB 显存反推的最大容量；输出和安全余量均为临时工程选值，尚未通过实际输出分布及目标 tokenizer 偏差校准。完整输入计数已经包含指令、证据、JSON schema 和消息封装，安全余量不是再次扣除提示词长度。

该 profile 用于保留一个可比实验条件，不能据此认定所有比赛候选或 API 对照均只能使用 128K。Qwen3.5-122B-A10B 官方原生上下文为 262,144 token。各候选应分别记录原生支持范围、量化权重和推理引擎，再校核实际可用显存与完整输入；128K 和 256K 的结果必须标明各自预算身份。当前未完成 H800 容量实测，没有证据证明更大上下文装不下。

Qwen 官方还提供通过 YaRN 扩展至 1,010,000 token 的配置，但这也不是单张 H800 的部署验收。是否能运行更大窗口，要同时满足模型支持范围和实际显存预算：驻留权重 + KV cache／线性状态 + 推理工作区及预填充峰值 + 审查阶段仍常驻的辅助模型 + 设备余量。若辅助模型串行卸载，必须观测实际释放后再计入审查阶段预算；不能既假定卸载又把相关模型视为随时可调用。

| 项目 | 本次方案 |
| --- | --- |
| 比赛资源 | 1 × H800 80 GB；27 vCPU；250 GB RAM；650 GB 高性能存储 + 1,250 GB 普通存储 |
| 主候选 | GPT-OSS-120B MXFP4，单请求审查，BF16 KV cache；H800 上的实际吞吐与峰值尚未验证 |
| 证据原则 | 先保全解析及原生表格，再按相关引用组成完整组；仅完整输入计数决定是否可送审 |
| 用户检查 | 提供切片／向量条目、逐页 OCR、任务召回与 rerank 前后及最终送审材料的检查界面 |

### 效果判断边界

已经确认并修复的基础问题包括长文本窗口静默截断及原生表格传递不完整。本轮还修正旧字符门控和相关引用分包。当前没有新的完整模型审查质量结果，因此不能声称漏报率、准确率或综合效果已经达到比赛要求。

代码测试、向量写入与探针留证用于证明流程行为；端到端质量必须由固定评价集、真实模型输出及人工核对证明。

## 1  模型与显存预算

| 候选 | 已核事实 | 部署判断 |
| --- | --- | --- |
| GPT-OSS-120B | 117B 总参数、约 5.1B 激活；原生 131,072 上下文；官方 MXFP4 原始权重索引 65,248,815,744 字节，约 60.768 GiB | 首选验证候选。官方可单 H100 运行；这不等于本项目已在 H800、128K 总窗口下实测通过；输入与输出合计必须在该窗口内 |
| Qwen3.5-122B-A10B | 原生 262,144 token；48 层：12 全注意力 + 36 线性注意力；128K／256K BF16 全注意力 KV 分别约 3／6 GiB，另有线性注意力状态；官方 BF16 权重约 232.99 GiB | 单张 80 GB 需要可用量化权重与兼容内核。第三方 Q4 必须验证格式、质量及长上下文，不能只凭激活参数判断可装载；尚未证明 256K 不可部署 |
| 27B／32B 对照 | 可用于预算、吞吐或质量对照 | 保留实验记录；不作为默认比赛审查模型 |

### GPT-OSS 的 KV cache 推导

配置为 36 层，其中 18 层全注意力、18 层滑动窗口注意力；8 个 KV heads、head dimension 64、BF16 每元素 2 字节。按每个 token 的 K 与 V 计算：2 × KV heads × head dimension × dtype bytes × 注意力层数。

128K、单序列、滑动窗口 128 正确保留时，KV 理论值约 4.505 GiB。若运行时为全部 36 层保留全长 KV，上界约 9 GiB。运行时的块对齐、工作区、CUDA graph、前缀缓存和并发都会增加占用，不能把理论 KV 当成最终峰值。

| 显存项 | 128K 串行规划 |
| --- | --- |
| 全部专家权重 | 官方原始索引约 60.768 GiB；存储字节与运行时驻留仍需区别 |
| BF16 KV cache | 滑窗正确保留约 4.504 GiB；全层全长保守上界 9 GiB |
| 工作区与设备余量 | 分别预留 6 GiB 和 4 GiB；均为规划假设，需实测核对 |
| 审查阶段辅助模型 | OCR 当前为 CPU 路径；GPU embedding／rerank 必须先显式卸载并观测释放 |
| 合计与硬件验收 | 滑窗规划约 75.272 GiB；全层全长约 79.768 GiB，余量很紧。以实际 GPU 可用字节和峰值验收 |

GiB = 2^30 字节；80 GB 的产品标签不直接替代实际 device.total_memory。128K 是 GPT-OSS 候选测试档，尚未 H800 压测，不代表硬件通用上限。16K token 安全余量与上述 4 GiB 显存余量是两项不同的预算。GPT-OSS 的 256K KV 算术值不代表其原生支持 256K；Qwen 的 256K 原生支持也不代表某个量化版本已在 H800 上运行通过。

补充实际计数：生产 Q6 全局输入的 MiniMax 计数为 108,855，按现有 98,304 门限被标记为 `over_budget`，但 108,855 + 16,384 = 125,239，仍低于 131,072；因此该结果只证明超过了含额外 16K 余量的测试政策，不能称为模型或 H800 无法容纳。关联完整证据组的独立计数为 13,728，可通过当前政策。两次均为供应商输入估计、没有生成调用；这些数字不能冒称目标模型 tokenizer 精确计数或硬件容量验证。

## 2  数据与检索流程

| 步骤 | 实现方式 | 检查重点 |
| --- | --- | --- |
| 原件与解析 | 逐文件保存 source hash、解析状态、页／块／字符位置；原生 PDF 文本优先，扫描页走 OCR | OCR 误识别、漏页、阅读顺序、空白页与表格重构分开记录；无法确认的页标 needs_review |
| 切片与窗口 | 语义父切片保留完整原文、表格行／单元格、条款所属与来源；模型输入窗口按 tokenizer 拆分 | 当前 embedding 和 rerank 窗口上限 512 token、重叠 64；原父文本不因此裁短 |
| 向量与词项召回 | 保留 BAAI/bge-m3 与独立 BM25 召回；保存 dense、BM25、RRF 排序与来源 | 固定与现场材料都走同一通用协议；签名绑定模型、分词器、数据和窗口配方 |
| 重排序 | BAAI/bge-reranker-v2-m3 对候选窗口打分；按已记录聚合策略回到完整父切片 | 每个任务可见 query、前后 rank／score、窗口、入选或排除原因，不能只看最终 topK |
| 证据排包 | 相关原始来源及其已识别引用优先同组；完整组超过预算时才在完整请求边界拆分 | 分包、缺失引用、未知来源、超预算和计数失败分别显示；单包可读不等于联合比较完整 |

### 固定资料与现场变动资料

NTT、SCT、SCC 模板以及 GCT、GCC、SL 可离线预解析、预切片、预嵌入后随包上传。现场其他文件不同，必须从原件重新解析、切片、嵌入与查询；不得依赖当前文件名、内容答案或评价集目标字符串。

标准包应包含权重／分词器版本、原件与切片 hash、索引签名、解析及 OCR 质量标记、重建脚本和验证记录。现场检查签名一致性；实际 Linux／H800 导入与检索仍需要赛前演练。

### 已经有的数据证据

当前 44 份材料的 native-v3 索引包含 13,464 个父切片和 13,602 个窗口；独立读取核对了索引载荷、范围与向量。13 个标准资料页面仍需人工复核。这个索引版本尚无新的完整检索评价运行，因此旧版本任务结果必须单独标识。

## 3  前端检查界面与审查 harness

| 页面 | 应显示的真实信息 | 验收方式 |
| --- | --- | --- |
| 切片与向量库 | 数据集／索引版本；文件、角色、页或条款；父切片全文；原生表格；embedding 窗口、维度与来源 | 从文件定位到切片，再定位到向量窗口；可分页、搜索、查看全文和原件；live 与 saved 快照分开标识 |
| OCR 逐页检查 | 页号、提取来源、文字、质量状态；对应原件入口；可用时显示页面图像／框 | 抽查扫描页、表格页、数字、否定词、页脚；缺少页面图像或人工校对就明确显示缺失 |
| 任务召回与 rerank | 真实 query；dense／BM25／RRF／rerank 候选；前后 rank／score；最终选取与送审材料 | 检查重要条件是否被召回、被降序、被 topK 或排包挡住；旧任务不冒称新索引结果 |

### harness 的职责

采用可观察的状态流程：来源冻结 → 检索 → 重排序 → 关联证据组 → 完整输入计数 → 模型调用 → 输出解析 → 引用与来源校验 → 人工复核 → 导出。每个阶段保存输入身份、参数、输出、耗时和明确状态。

输入门控读取完整消息及 schema；当前临时 GPT-OSS 候选政策以 98,304 token 为输入边界，超出则完整分包。该数不是 H800 的通用容量上限。计数未知、网络失败、材料不完整和模型空结果分开记录。计数结果只是预算估计；供应商 token 与最终模型 tokenizer 的差异需要单独校核。

单包结果只能引用该包实际提供的来源。跨包归并通过明确的引用与来源身份校验，不能把某条款在不同包分别出现解释成模型已做过联合比较。

### 是否需要 agent runtime

先保留自研的有界调度与明确状态机，避免框架替换掩盖数据问题。只有在证据齐全、输入预算正确、输出校验通过后，仍出现可重复的规划或多轮取证失败，才比较工具循环或开源 agent runtime。模型能力、提示词和工作流的对照应使用同一材料、预算与评价集。

### 接下来的三次可交付验收

第一步：用户能打开检查页，核对真实切片、OCR 页和任务 rerank。补齐发现的数据错误并记录具体文件／页／切片。

第二步：用相同材料、明确标识的候选窗口与输入政策重跑排包及输入计数。现有 128K 档保留为对照；Qwen 的原生 256K 应独立核算，不能被 GPT-OSS 的窗口假设排除。逐请求核对旧门控阻挡是否解除、必要条件是否同包、超预算或未知是否公开显示；旧结果与新结果分别留存。

第三步：在证据验收后用 MiniMax 完成审查对照，按人工标注评价召回与漏报、误报、引用正确率、条件完整性、无效输出率和端到端耗时。比赛模型到位后在相同基准上复验。

每次实验固定材料与模型／索引身份，记录参数、提示词、完整输入、各阶段候选及分数、原始输出与失败。优先改变一个关键变量；评价标签只用于验收，不进入生产召回或证据排序。
