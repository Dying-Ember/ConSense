## 1. 结论与策略优先级

最适合本项目的组合是：**资料导入阶段顺序运行完整双解析与文档 embedding；资料就绪后保留 LLM，查询时执行 query embedding／rerank；显存不足则受控切换。** 固定版本成果持久化，使正常冷启动与后续提问无需重跑固定库 OCR 或文档 embedding。OCR 与 LLM 的互斥允许大模型在业务阶段使用接近整卡的资源，不必为 OCR 长期留出一块显存，更不必仅为 OCR 常驻而强迫改选小 LLM。

工程上先建立能可靠退出、释放、重载和恢复的基线，再优化成引擎 sleep／wake 与兼容量化权重 RAM 缓存。两种机制可以保留为互相回退的路径：优化失败时退出自有 worker 并从冻结权重重载，继续使用同一模型和配方；不能在失败时静默换模型、降分辨率或截断资料。

仍需独立分析在线 embedding／rerank：它们是每个新问题的查询处理，不能把“固定文档向量已提前计算”理解成“提问时完全不需要 GPU 检索模型”。它们与 LLM 是否同时驻留由实测峰值决定；驻留可以同时，实际计算可继续串行。

**建议顺序**：可靠阶段切换 → 兼容量化权重热缓存／sleep → 在线 E/R 与 LLM 的有界共驻 → 已验收的精度或 KV 优化。MIG、MPS 与多 Pod 超额共享只在确有额外需求且平台支持时考虑，不作为这个互斥场景的默认解法。

## 3. 分阶段预算：峰值取最大值，而不是把所有权重相加

资料处理的推荐阶段如下。所有持久成果均绑定来源、范围、模型、源码与配方身份。

| 阶段 | GPU 驻留／工作 | CPU、RAM 与磁盘职责 | 进入下一阶段的条件 |
| --- | --- | --- | --- |
| 原生准备 | 不要求加载业务 LLM 或 OCR 主模型 | 识别原件身份、范围、原生结构；必要渲染；复用准确匹配固定成果 | 不把隐藏 OCR 层当可靠可见文字；准备完整待处理批次 |
| Paddle 完整解析 | Paddle 主模型与该配方必要辅助组件 | 完整保存 raw、结构、assets、失败与位置 | 本批次完成、输出落盘、自有 GPU worker 释放已观测 |
| MinerU 完整解析 | MinerU full 主模型与必要辅助组件 | 保存完整第二路；在 CPU 对齐、源核和形成完整采用单元 | 完整产物及采用／unknown 状态明确；释放已观测 |
| 文档索引准备 | BGE 文档 embedding；必要任务 query 的 E/R 分批串行 | canonical、词法检索、持久索引与 generation 发布 | 受影响范围通过对应来源／质量／索引门；不能只凭 index ready |
| 业务推理 | 恢复 LLM；视已验证 profile 保留 E/R，或查询时受控切换 | 业务状态、对话原消息、索引与引用回取保持 | 模型身份、ready、完整输入与容量准入通过 |

```text
阶段所需显存 = 权重驻留 + KV／线性状态 + 临时激活与工作区
             + CUDA graph／非框架分配 + 本阶段常驻辅助 + 安全余量
单卡要求 = max(各正常阶段峰值, 切换过程峰值) <= 实际可用设备字节
```

切换过程也必须入预算。先加载后一模型、再卸前一模型，会人为制造双份权重峰值。应先停止新请求、收尾当前工作、保存产物与状态、释放并观测，再加载下一阶段；CPU 可预读兼容权重，但不能偷偷提前占用 GPU。

GPU 的 allocated、reserved 与整卡使用量是不同观测，不能相加。另行测 RAM 峰值，包括 packed 权重缓存、框架张量、反序列化临时副本、pinned memory、OS page cache、解析资产和索引。不能因 250GB RAM 看似充裕，就假定量化模型加载过程中展开大规模 BF16 副本也安全。

## 4. 加载／卸载策略逐项比较

| 策略 | 怎么做 | 优点 | 成本与失败边界 | 本项目建议 |
| --- | --- | --- | --- | --- |
| A. 整进程退出后重载 | 完成阶段后退出所属 GPU worker，下一阶段启动对应 worker | 所有权容易归因、框架残留容易清理、不同依赖可隔离；可作为恢复基线 | 重建引擎、读取／映射权重、GPU 搬运、warmup 与 prefill 都有成本 | 必须保留的可靠基线；批次足够大时成本可摊薄 |
| B. 保留兼容 packed 权重 RAM 缓存 | GPU 释放后保留已验证可恢复的量化表示，或利用引擎正式 offload | 避免每个正常批次从磁盘冷读；符合已确认资源方向 | OS page cache 不等于可直接回迁的引擎张量；量化重排、host 副本与 pinned 内存仍需量测 | 默认优化方向；量化表示／实际 host 峰值通过才启用 |
| C. vLLM sleep level 1／wake | 引擎不退出；将权重 offload 到 CPU，丢弃 KV，之后回迁 | 减少进程和引擎重建；适合互斥阶段的正常切换 | 首次 offload 可能包含 D2H；wake 有 H2D；旧对话需要重新 prefill；模型／内核兼容和真实释放须验 | 优先验证的优化；失败回退 A，同模型同配方 |
| D. 深度 sleep／丢弃权重 | 释放更多状态，随后执行明确的权重重载流程 | 适合更新权重或特殊内存管理 | 丢弃权重后仅 wake 不能假定恢复有效原权重；需要重载与身份核验 | 不作为普通批次默认路径 |
| E. 只保留 LLM＋在线 E/R | OCR 卸载，LLM 热驻留；检索时运行 E/R，生成时回 LLM | 连续 Advisory 不必每问搬运大模型；OCR 仍能用完整双路 | 权重同时驻留，即使计算串行，显存也要合并计算；需给 E/R 最大输入激活留空间 | 业务阶段首选优化目标，须通过最大请求容量准入 |
| F. E/R 与 LLM 也分阶段 | 每问先让出 LLM，完成 query E/R，释放后恢复 LLM | 不要求减小主 LLM 或牺牲完整证据；容量适应强 | 连续问答会反复付切换与重新 prefill 成本；整批审查可批量取证后减少恢复次数 | 合法可行的容量回退，实际等待明确记录 |
| G. 推理过程中权重 CPU offload | 部分权重一直留 CPU，推理时按后端机制迁入 GPU，或由支持的后端在 CPU 计算专家 | 权重超过整卡时提供可行路径 | 与阶段卸载不同；可能在各层／各 token 重复跨主机通道，或受 CPU 专家计算瓶颈约束，延迟依赖内核和专家访问 | 仅候选确有容量缺口时对照，不作为首选常态 |
| H. KV cache CPU offload | 权重留 GPU；引擎把部分 KV 转到主机并按需访问／预取 | 为长上下文／缓存容量提供额外空间 | 访问带宽、prefill／decode 及并发开销需测；不同引擎旧 swap-space 与新 offload 参数不可混用 | 长上下文边界优化，不代替权重预算 |
| I. 权重量化／KV 精度优化 | 官方 MXFP4、FP8、GPTQ，或已支持的 KV 精度分别验证 | 直接减少所选阶段容量压力 | 格式／内核兼容、局部未量化张量、数值与业务质量退化需要分别评估 | 优先官方可复现权重；每种配方独立验收，不自动降精度 |
| J. 较小 LLM／按任务多模型 | 保留 27B dense、35B MoE 等作为可比候选 | 容量宽裕，更容易保留 E/R；可降低恢复成本 | 小模型并不保证合同条件推理同样可靠；多模型有路由与重复加载成本 | 作为质量与工程对照；不能因 OCR 不常驻仍硬性缩小主模型 |
| K. CPU 侧预读与预处理 | 在允许的状态中预读 packed 权重、渲染、整理来源与词法索引 | 不额外占 GPU，可以隐藏部分准备等待 | RAM 峰值、I/O 竞争、来源变化与取消处理仍需控制 | 低风险后续优化；不跳过 fresh-source 或质量门 |
| L. chunked prefill／有界 batch／减少 graph | 保持完整请求，分块处理 prefill，或降低 CUDA graph 捕获范围 | 可减小临时工作区／捕获峰值，不必削减证据正文 | 改变内核、调度和浮点路径需回归；无法消除权重或所需 KV 的固有容量 | 峰值归因明确后单因素比较，优于未经核验的内容截断 |
| M. text-only loader／明确关闭未使用 MTP | 仅实际任务需要文本时，通过引擎正式入口不加载视觉／投机组件 | 可能减少权重与 profiling 开销 | 必须保存实际载入张量与省下的字节；不能在完整索引上凭空扣除，也不能改已有图像能力承诺 | 精确能力与模型身份核定后评估；本文完整 checkpoint 数字仍保留 |

vLLM level 1 的行为与 GPU 释放边界依据 [v0.19.1 sleep 文档](https://docs.vllm.ai/en/v0.19.1/features/sleep_mode/)。`torch.cuda.empty_cache()` 仅清理未使用 allocator 缓存，不释放仍被引用的模型；原理见 [PyTorch 官方说明](https://docs.pytorch.org/docs/stable/generated/torch.cuda.memory.empty_cache.html)。当前 E/R 代码先删除另一模型再清缓存，仍没有证明其他进程、LLM 或 OCR 已释放。

### RAM 缓存与 offload 不能混为同一种实现

磁盘文件已在 OS page cache 中，只能说明冷读可能减少；进程重启仍要执行 loader、反序列化／映射、量化重排和 GPU 初始化。引擎 level 1 则保留可恢复权重状态，其第一次 sleep 通常会执行权重 offload。不能因为 RAM 中“已有相同文件”，就假定引擎会自动跳过 D2H、恢复执行图或共享同一份量化张量。

普通权重不变时，工程可以研究避免冗余 GPU→CPU 回拷的正式 loader／cache 路径；这种自定义优化需验收，不能将通用 `.to('cpu')` 用作所有量化格式的保证。若 sleep 引擎进程被 Pod 重建杀死，进程内热缓存也会丢失，应自动走已验证的冷／暖文件重载恢复。

存储可按使用频率组织：高性能盘优先放最终已选模型、完整parser必需资产、当前有效索引与正常恢复路径；通用盘保留原件、完整双路证据与候选归档。不要默认650GB快盘能同时保留所有候选版本／精度、解压临时副本和全来源资产。正式冻结前逐文件清单计算持久量和构建峰值；迁到慢盘、保留page cache与保留packed RAM缓存有不同恢复性能，都需记录，原件和失败证据的保全要求不因此改变。

| Qwen3.6-35B-A3B 官方 FP8 | 官方文件大小量级约 34.89 GiB；此处为文件长度口径，不能与 payload 精确相减 | 与 3.5 分开固定版本评估；发布宣传并非合同质量结论 | 新版补充对照；不把 3.5 称为最新 |
| Qwen3.5-27B dense BF16 | payload 约 51.747 GiB；原生 262,144 上下文 | 权重较 120B 量化模型更小，但其 attention／KV 配置不同，长上下文仍可能很贵 | 不以激活参数排名的 dense 质量对照 |

每个字节值的官方索引 URL、revision、获取口径与重算依据见 [LLM 研究](./research/llm-h800-selection-20261012.md)。来源包括 [GPT-OSS 官方规格](https://developers.openai.com/api/docs/models/gpt-oss-120b)、[Qwen122 GPTQ 官卡](https://huggingface.co/Qwen/Qwen3.5-122B-A10B-GPTQ-Int4)、[Qwen35 FP8 官卡](https://huggingface.co/Qwen/Qwen3.5-35B-A3B-FP8)、[Qwen3.6 官卡](https://huggingface.co/Qwen/Qwen3.6-35B-A3B)。这些是第一方说明与文件事实，均非本项目推理实测。

更广的8B／9B、27B官方FP8、Gemma31、GLM Flash、72B AWQ与M3 API参照见 [任务候选矩阵](./research/llm-task-model-candidates-20261012.md)；它们按任务与资源参与评价，当前表不是主模型排名。M3已有官方开放权重，但约428B总参数的整模型单H800驻留不成立，官方多卡self-host与单卡部署分开，见 [M3专文](./research/minimax-m3-evaluation-reference-20261012.md)。

**为什么 120B×0.5 bytes 不能决定选型？** 只是一切参数都恰好 4bit 的算术下界。量化 scale、未量化 attention／embedding／输出层、视觉部分及引擎表示都有额外成本。Qwen 官方 Int4 的实际 payload 已达到 73.429 GiB，正是必须读准确权重清单的例子。MoE 少量激活参数主要减少计算量，不能据此只给 GPU 预算激活专家；专家 offload 是额外的引擎方案，需单独验其访问与迁移成本。

### 可复算的 KV／状态边界

对普通全注意力层，单序列理论 KV 为：

```text
KV bytes = 2(K与V) × KV_heads × head_dim × dtype_bytes
         × attention_layers × (输入 + 已生成token)
```

GPT-OSS 配置的 18 个 full＋18 个 window-128 层、8 KV heads、head_dim 64、BF16，131,072 总 token 的理想分层存储约 **4.504 GiB**；若引擎对全部 36 层保留全长，上界算术为 **9 GiB**。实际 block 对齐、hybrid cache 分组、前缀缓存与并发配置可能产生额外保留，必须看引擎真实分配。

沿用旧计划的 **6 GiB 工作区＋4 GiB余量** 作为纯场景假设：60.768＋4.504＋6＋4＝**75.272 GiB**；保守全长 KV 情景为 **79.768 GiB**。两项不是实测。若还要 E/R 驻留，必须在这之外计入相应常驻张量与最大检索激活，不能说“80GB 所以肯定够”。产品标签、GB／GiB 与实际 total_memory 要分开。

Qwen122 的 12 个 full attention 层、2 KV heads、head_dim 256、BF16，在 128K／256K 的 full-attention KV 分别为 **3／6 GiB**；还有 36 层线性状态、工作区与缓存策略。73.429＋3＝**76.429 GiB**；73.429＋6＝**79.429 GiB**，都还未加这些其他项目。因此其原生支持 256K 和单卡短输入可启动，不能推出单卡 256K 的工程配置安全；也不能在未测时一概断言所有 offload／engine 方案都不可运行。

Qwen35 的理论 full-attention KV 在 128K 约 2.5 GiB，Qwen27 约 8 GiB，另加各自线性状态等开销。较小 dense 模型未必比较大混合 MoE 更省长上下文缓存，不能统一套用一个“每 token 显存”常数。

### 业务质量怎样决定主选

候选在同一冻结来源、同一必要证据包和同一评分口径下比较：条件／例外和否定保持、项目实际采用版次、跨文件矛盾、引用原文忠实性、unknown 处理、完整表组，以及 Vetting schema／报告完整性。先给足正确材料，再判断模型是否推理失败；不能把解析漏条款、rerank 漏条件、metadata 巨型序列化或分包错误归因给模型。

两轮评价应分开：第一轮统一完整材料和可比生成预算，评价纯业务质量；第二轮允许各模型用通过验收的自身上下文／量化／引擎配置，比较完整部署质量、尾延迟和资源。生成预算包含 reasoning＋final 输出，不能只给最终报告计 token。

GPT-OSS 是文本输入模型，不能承担尚未验证的原图理解；本项目首版按 Q10 返回可定位原图，不因换成多模态 Qwen 自动扩展图形关系判断。GPT-OSS 还需正确 Harmony template／reasoning parser，结构化 schema 要验推理引擎实际约束与 final 输出处理；提示中有 JSON schema 不等于保证合法 JSON。依据 [OpenAI Harmony 官方说明](https://developers.openai.com/cookbook/articles/openai-harmony)。

## 6. 在线 E/R：两个可行模式，无需修改业务逻辑

**模式一：LLM 热驻留，E/R 有界驻留。** 为 LLM 明确最大总 token、活动序列、KV 字节与工作区预算；剩余空间根据真实 E/R FP32 或新验收精度的峰值留出。查询取证与 decode 继续串行，可降低叠加激活峰值。E/R 可以一套一套装载，或同时驻留以减少反复加载，但各自预算不同。

`gpu_memory_utilization` 是单个 vLLM 实例的预算／分配参数，不是多个进程共同的显存隔离。不能把两个 engine 都设 0.9，或者简单把大 LLM 改成 0.8 就认定安全。若准确版本支持 `kv_cache_memory_bytes`，可用已测需求明确 KV 池，同时测权重、workspace 与 E/R 余量；参数不会自动限制其他进程。详见 [GPU 调度研究](./research/oer-h800-memory-scheduling-20261012.md)。

**模式二：query E/R 与 LLM 互斥切换。** 新 query 先完成完整来源核验、query embedding、召回／query-bound rerank 和证据排包，然后释放检索模型、恢复 LLM 生成。它保持质量与单卡约束，只是每次新问答可能产生迁移和重新 prefill。Vetting 的已知任务 query 可批量准备、一次恢复 LLM 处理多个包；后续追加检索或未知 Advisory query 仍需新的调度，不能把“批次一次恢复”外推到所有交互。

固定库向量属于文档准备结果，query 向量和 rerank 分数属于当前问题。允许复用纯计算结果也要准确绑定 query、来源 generation、模型与配方；不缓存 fresh-source verdict，不把某题排序作为下一题的通用事实。

## 7. K8s：VRAM 空闲与 GPU 资源可调度是两件事

最容易落入的错误是：LLM Pod 请求了唯一的 `nvidia.com/gpu: 1`，调用 sleep 后显存已释放，随后启动同样请求一张卡的 OCR Job。**sleep 只改变进程显存，通常不会释放 K8s 分配给原 Pod 的 GPU extended resource，OCR Job 仍可能 Pending。**

| 组织方式 | 适用性 | 实际代价 |
| --- | --- | --- |
| 一个 GPU 所有者容器，协调不同独立 worker／环境 | 当前单卡互斥任务的优先候选；K8s 持续只分配一个 GPU resource，所有者管理阶段 | 不把 Paddle、MinerU、LLM 全塞进一个 Python 解释器；依赖隔离、worker 退出／sleep、恢复与状态持久化必须实现 |
| 独占 LLM Pod 与 OCR Job 依次终止／创建 | 平台要求各组件独立镜像时的清晰基线 | 要让调度资源真正释放；LLM 进程 RAM 热缓存会随终止消失，不能仍承诺原进程 wake |
| 多 Pod time-slicing＋应用统一协调 | 平台支持共享设备、必须保留独立 GPU Pod 时可研究 | time-slicing 不隔离显存或故障；跨 Pod 锁、存活／回收、峰值和权限更复杂 |
| MPS | 可对共享进程计算资源进行约束，具体 device plugin 有份额边界 | 固定均分可能把约 60GiB LLM 限制在不足的份额；没有本项目并行计算需求，不优先引入 |
| MIG | 硬件隔离在平台允许且规格支持时有价值 | 分成较小实例会压缩大 LLM 所需连续实例容量；互斥任务无须长期切掉可用整卡 |

time-slicing 的无显存／故障隔离是 [NVIDIA GPU Operator 官方明确边界](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/latest/gpu-sharing.html)。跨进程／Pod 调度必须按实际模型所有者协调；租约超时本身不证明旧 worker 已停止，回收前须确认实际进程和设备释放。CPU API 服务及业务状态可继续运行，避免把 GPU worker 重建等同于用户会话丢失。

Qdrant Local 仍是文件式单进程所有者，不能多个 Pod 直接共写同一路径。后续可维持明确单写者，或在工程恢复时验证服务式 Qdrant 与持久卷。此次研究不迁移数据库，也不把 K8s 组件拓扑写成已实施。

## 8. 切换耗时应该怎样估算与验收

```text
正常批次切换成本 = drain + 释放/必要D2H + 下一引擎准备
                 + 权重H2D + warmup + 首次重新prefill
冷恢复还包含磁盘读取、loader及必要的量化重排
```

以 60×10^9 bytes 权重和 **假设**有效 H2D 8／12／24GB/s，纯搬运下界为 7.5／5／2.5 秒。这是 W/B 算术，不是 H800 实测；不能使用 HBM 内部带宽作主机→GPU 分母。读取、搬运可以流水重叠时要测端到端真实时间，不机械相加。实际权重为 65.25GB 或 78.84GB 时，要代入各自实际表示，不能继续使用 60GB 估算。

把两套 parser 按完整批次跑完，可把大 LLM 恢复次数控制在正常批次的一次；每页在 LLM 与 OCR 之间切换会按页数放大成本，本项目没有这种需要。首次问题 TTFT 还包含重新 prefill／reasoning，ready 健康检查成功并不代表用户已收到答案。

| 必测情景 | 记录项目 | 通过含义 |
| --- | --- | --- |
| 同版冷启动 | fixed generation 校验、索引恢复、模型加载次数 | 不重跑准确匹配的固定 OCR／文档 embedding；真实来源校验保持 |
| 完整新资料批次 | 两路完整 parser、采用／unknown、文档 embedding、发布、一次正常 LLM 恢复 | 新版本真实处理完成；旧完整 generation 不被半成品覆盖 |
| 引擎 sleep／wake | 睡前／睡后整卡、host 峰值、D2H／H2D、身份、ready、首题及后续题 | 准确模型可恢复；旧 KV 丢弃被正确处理 |
| 最大业务请求 | 实际 tokenizer 完整输入＋reasoning/final 预算、最大检索组、序列数 | 通过指定 profile 的容量和正确性；不是任意长输入通行证 |
| 连续 Advisory | 每问 E/R 加载次数、LLM 切换次数、TTFT、总时延及队列 | 识别常驻与阶段回退的真实用户等待成本 |
| 取消／失败／OOM／worker崩溃 | 实际 owner／进程、部分结果、释放、恢复和重试身份 | 不并发争卡、不覆盖旧成果、不静默降级；仅恢复自己的任务 |
| K8s 重建 | GPU resource、PVC、来源／索引、配置和 ready 状态恢复 | 进程缓存丢失时仍可安全重载，CPU 业务状态保持 |
| 业务质量对照 | Advisory 逐题必要证据与引用；Vetting 完整 schema／发现／条件 | 模型和部署配方通过真实业务门，与代码测试分开 |

重复测冷、暖与连续状态，报告样本数、中位数和尾延迟；不以一次加载日志冒称稳定性能。A4000 上的小模型加载或 Linux 两页 full 记录只说明对应本地环境，不能替代 H800 的 120B 迁移结果。

## 9. 后续实施顺序与未决事实

现阶段继续范围内原件解析质量工作。本轮无需用户重答硬件、业务范围、双解析或质量优先；工程事实由执行者查证。

恢复部署工程后，先建立准确模型／引擎身份与 Linux 冻结依赖，再验证阶段退出重载基线；随后验证 RAM packed 缓存和 sleep／wake，最后测 LLM＋在线 E/R 的最大 profile。若共驻不通过，使用同模型的查询阶段切换；若大模型长上下文本身容量不足，才比较已验证 KV／权重 offload、精度或其他候选，不悄悄减掉完整资料。

须继续核的事实包括赛方实际 LLM／可替换权限与端点控制能力、目标 K8s resource 模式、准确 GPU 可用字节、引擎量化内核与 host 缓存表示、真实加载／恢复与最大请求峰值。它们当前没有目标实测证据；这不妨碍确定互斥阶段作为设计前提，也不构成再次让用户选择业务逻辑的理由。

本轮仅完成研究文档、既有配置只读核查与算术重算。没有加载新模型、修改在线配置／源码、重启服务、提交／推送、上传发布包或操作比赛集群。
