## 问题

比赛现场有 48 小时用于调试代码和产出最终结果。镜像打包后不能现场修改，但冻结基线只有 Java 可执行包与前端构建产物部分外置；部分项目启动脚本和 Python 代码仍在镜像中。候选离线入口与现有资料读取入口不同，模型有限任务方式明确不支持逐段正文输出。直接部署会使现场难以修改业务代码，也有使冻结基线已有接口、数据流和功能缩水的风险。

任何时刻最多允许 5 个容器；业务模型为团队自行在 H800 部署的 Qwen3.8 27B。本机先按比赛约束完成真实容器预演，实际硬件、权重格式和推理方式必须核对。业务、前端、配置、模型、数据库、原件和运行记录需要在硬盘上可持续保存。需要有足够的日志定位问题，并在允许的受控短暂停机内完成版本替换，保护进行中的工作与历史数据。

**工作边界：**本次主交付是将冻结基线中的现有业务代码、前端和需迭代的项目脚本从镜像中剥离到硬盘，由固定运行环境继续执行；配置文件、必要日志、启动及切换、数据路径和文档是配套。只做为代码外置、五容器限制、本地模型接入和不降低冻结基线已有功能所必需的调整。用户明确此前未完成的工作全部作废、不要继续：以前的待办、未完成验收、候选方案或实验不转入本次目标，也不是本次工作的前置条件。冻结提交保留为完整历史和行为对照，重构可移动或修改实现；历史文档、原件、数据与证据不因旧工作作废而被删除。对本次改造新引入的故障或导致基线已有功能缩水的问题必须处理，不借此恢复以前未完成的工作。

## 目标方案

镜像和容器尽量最小化，只提供确实需要留在镜像内的运行时及依赖；凡能放在外面的文件尽量放硬盘，包括业务与前端源码、运行产物、项目脚本、可调整配置、模型及配套文件和持久数据。只有经核实确实无法外置的内容才留在镜像中，逐项说明原因及修改影响，不能因为打包方便就把可外置业务文件留在镜像里。使用现有功能入口与结果约定，接入自部署的本地模型，保留冻结基线实际已有的资料处理、逐段输出、停止及用户可见功能。在本机实际构建或加载运行镜像、挂载上述文件并启动完整系统，完成真实业务试运行。部署、更新、失败恢复和任务运行期间全程满足容器数量限制。

优先评估能否复用现有部署和任务执行方式；只有现有方式无法同时满足容器数量、现有功能、实时输出及资源清理要求时，才进行最小必要调整。一个固定的显卡执行位置、连同应用、资料协调、MySQL 和 Qdrant 构成五个职责位置，是可研究的方案，**不是预先决定必须新建的系统，也不是现成实现或目标环境验收。**固定位置与临时任务的选择须满足相同要求，两种方式不能同时占用额外容器。

保持业务并发现值、思考关闭和当前已采用的稳定 OCR 实现；不在本次工作中新增模型训练、微调、换型比较或模型参数消融，也不替换 OCR。必要运行参数外置、环境适配和工程修复仍在范围内。允许受控短暂停机，切换前处理进行中的任务和已保存数据。模型具体文件、推理程序、模型协议和现场能力须按实际核对，不能从历史研究假定已被采用。

## 实施决定

### 现状与改造范围

- 目前仅有外置 Java 可执行包和前端构建产物的本地第一步；项目启动脚本及协调、显卡任务相关 Python 代码仍存在于镜像。启动定义、部署生成和任务执行时覆盖命令均须一起核对。固定显卡执行程序、完整文件外置和赛方环境运行尚未完成。
- 现有离线资料入口与统一资料入口存在差异，须按冻结基线实际已有能力和实际使用的请求逐项对照；不得用健康检查、普通检索或部分 OCR 入口替代基线已有功能，也不将此前未完成的资料工作恢复为本次目标。
- 现有有限显卡任务拒绝流式正文，现有部署配置也要求关闭该能力。需要贯通模型、协调、网关和页面，保留逐段可见、停止、失败、历史及引用；不能以最终一次性返回代替。
- 沿已有业务入口和资料处理方式组织实现。只在真实变化和完整功能需要的地方调整职责；不因文件大而整体重写，不新增平行的资料模型、解析流程或重复索引。

### 硬盘、镜像、配置和版本

- 硬盘保存业务与前端源码、完整构建产物、运行所需项目脚本、业务配置、模型权重及实际配套文件、关系及向量数据库数据、原件、来源及 OCR 证据、生成结果、任务状态和日志。区分只读版本资产、受控秘密与可写数据；不把数据库、密钥和原件放入网页可访问目录。
- 比赛运行环境不搬项目说明文档；spec、交接及部署说明继续在本地与远端仓库维护。程序实际读取的资源（包括以 Markdown 格式保存的业务提示策略）必须保留，不按扩展名误删。
- 镜像和容器最小化；运行时、第三方依赖、系统库及文件工具也先评估外置，确实无法外置时才留在镜像中。业务文件、项目脚本、规则、配置、字体、模型及其他文件均按同一原则逐项检查；记录不能外置的具体原因和后果，不能以实现方便替代判断。平台内核与显卡驱动由目标环境提供并核对兼容性。
