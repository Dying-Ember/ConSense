# Drafting harness 的版次基线与原子识别协作

本稿记录用户已确认的产品边界和待核实的实现路径；不是已实现或验收通过的声明。目标是提高图谱与项目候选的准确性，减少需要人工逐条整理的重复事项，同时保持轻量、可追溯和人工可修改。

## 已确认的行为

1. 保留现有原子语义能力。相同来源中一个事实可能关联多个原子处理环节；原子结果、指导说明和修改对象不因此各自变成独立项目输入。
2. 对来源、版次及内容均已核对的可用图谱基线，优先恢复已核部分并绑定本次原件；完整同版基线无需每次全量重新识别，差异、疑点或使用者主动要求才进入补充识别。待核部分不得假称完整。
3. 有依据的同义输入在待审核草稿中归到同一变量，分别保留来源、前提、与／或／非条件、分支和各自修改范围；不确定或不等价的候选单独列为例外。
4. 使用者可按组确认对应本版且有依据的图谱部分；其余变量或关系保持待核。已确认变量可先用于项目候选提取；候选、人工采用和最终原件修改是分开的决定。
5. 后续变化只使受影响的定义、关系、候选或范围重新待核，并保留旧记录；人工明确标为适用于该模板版次的修正可在同版新项目中作为待审核内容复用，不带入项目专属答案或改写其他项目。
6. 允许模型按需调用有限工具获取相关固定图谱、当前版原文和相关关系，并生成待审核草稿；模型不直接采用项目值或修改最终文件。准确率优先，耗时如实测量，不以 30 分钟为硬上限。
7. 条款版本与文件格式分开识别。某一 SCC 内容版本可能以 PDF 或 Word 出现；跨格式复用逻辑前核对版次与内容，具体位置和可编辑范围重新绑定当前原件。

## 拟议的数据流

1. **识别来源与基线**：保留 OER 的本次原件身份和观察，按真实内容及版次寻找可用基线。字节完全相同可作为强身份线索；跨格式按条款、指导说明和结构证据核对，不能只凭文件名或条号。旧基线本身的缺口或错误不得升级为已确认事实。
2. **恢复业务图谱**：在现有项目图谱及版本链中复用已核的业务变量和有据影响链；保留项目、原件和历史版本隔离。固定图谱的变量、条件、派生、目标与各处证据各自可追溯，避免把整图重复搬入每次模型输入。
3. **处理变化及疑点**：将相关指导说明、标记与 OER 范围挂到对应局部影响链。对确有差异、缺失、冲突或无法确认的地方，再调用已有原子能力及必要的局部上下文；模型可请求更多证据。编辑目标始终属于当前原件，引用或指导说明不能直接充当编辑范围。
4. **输出审阅结果**：对足以归为同一变量的候选构建共同根并保留所有局部范围；复合条件不得压成其中一个输入。例如“设计并施工”不得仅按“设计”判为等价。只对有证据支持的部分提供整组确认；其余留在例外列表，保留人工修改和原子来源。
5. **提取与变更**：从已确认的业务定义中提取有项目来源的候选，未确认的定义不作为已确认输入。定义或关键前提改变时重新核对受影响内容；与该变化无关的确认、候选及人工值不应被整体清空或强制重审。

## 三个需要通过的业务例子

- **BQ 发放**：`L10Pro`／`Hardcopy` 是共同输入；NTT 2 的两个方案、NTT 3(c) 的两个方案及其他受影响位置各自保留来源和范围。NTT 3(c) 的标准 Envelope 2 文字还依赖双信封前提；前提不明时不能只按发放格式自动删除另一段。
- **屋面与避火层**：屋面安装／保修和避火层安装／保修是不同事实；同一个指导说明中多次出现的相同事实可共用变量，但各个标记位置及其处理分别核对。不能把屋面保修映射到避火层保修。
- **NTT 10 保证金**：保留原句 `combined contracts with foundation works` 与不少于 39 个月的完整条件；在缺少更多权威定义时，不将 `combined contract` 猜成“基础工程加上部结构工程”，也不能仅凭“包含基础工程”代替完整条件。

## 工具与约束

优先扩展现有按需取证流程，提供小而明确的能力：查固定变量及其相关条件链；按版次读取本次原文和相邻范围；查相关已识别观察及关系。每次只返回判断所需的内容，允许按需多轮补充，并保留请求、证据、结论、缺口及失败状态。是否接入模型服务的原生 tool calling 取决于实际服务能力，不预设它已支持；无需为此先引入通用重型 agent 框架。

程序应校验版本、来源、引用、类型、条件与范围等可确定约束；模型说“语义一致”或给出高分不足以证明事实正确。无法证明的映射不能变成已确认图谱或可执行编辑。已核基线遇到与原文不符的证据时，相关链留待核查，未受影响的已核部分仍可继续。

## 预期修改接缝

- `DraftAutomationService`／`DraftAutomaticDiscovery`：在现有 OER 观察和自动任务链内加入版本基线选择、同版复用及差异驱动的原子识别；保留原始识别和调用记录。不能以文件名或模拟题答案做特例。
- `DraftBaselineMatcher`／现有固定目录和业务规则：按当前业务语义簇提供相关定义和关系，保留未验证、部分对应和冲突；不能把一项复合条件缩成一个相似字段。固定规则和清理绑定以来源和覆盖状态为准，不把历史资产直接升格为已证完整图谱。
- `DraftReviewDiscovery`／`DraftBusinessRules`：移除 NTT `combined contract` 无依据的固定解释，并根据原句核对 G1a 的完整前提；不擅自发明项目事实，也不简单删除旧值或历史。其余原子识别能力继续保留。
- `DraftTemplateGraphService`、现有图谱审核和取值界面：支持按组确认、仅对已确认子集提取以及按实际影响重核。同步检查定义与来源指纹、旧候选及人工值、图谱版本、预览和生成调用方，避免仅放松全图门槛后误用旧候选。
- SCC PDF 参考与 Word 规则维持各自来源绑定。逐页调查形成的图谱和跨格式对应经核对后接入同一业务图谱链；不能把某版的页码、段号或条文编号当成另一原件的编辑坐标。

## 当前证据与待解决事项

- 本轮 2a NTT、SCT 和 Word SCC 上传件与原件的字节哈希相同，但流程仍产生 473 个业务候选与 8 个来源核查事项；数量本身不是准确率。此前人工核对的 NTT 3(c) 两个分支遗漏双信封前提，尚须更正并复测。
- 固定目录、业务规则与部分来源绑定仍在；208 条编制说明／标记清理绑定不是 208 条业务影响链。历史 Word 完整分析曾记录 79 个业务定义与 45 条链，原结构化文件的现存备份仍在查找；不能把代码和历史报告直接称作已完成的新基线。
- 屋面保修错配避火层保修、设计并施工被简化为仅设计，是本轮有针对性的失败样例。NTT `combined contracts with foundation works` 被当前提示词作无原文依据的定义，相关固定规则也需连同原文前提核查。
- PDF 来源的 SCC 内容版本正逐页调查；不得因为现有参考文件是 PDF 就排除比赛中可能提供的同版 Word。所有新增证据与运行产物保存在 D 盘。

## 验证边界

以同版基线复用、存在局部差异的新版本和两种 SCC 内容版本为不同场景，对照原件及独立保留的参考答案，分别核对变量身份、条件链、与／或／非、分支、跨条引用、原文范围、缺失与多余项。测试要证明同一事实的多处范围保留，且不把不同事实误合并；记录用户实际审核与修改成本。

产品验收通过真实前端上传、确认、提取、人工修改、预览和导出；保留失败与截图、按操作分叉记录，并检查三份输出。软件测试、模型调用、源文质量和前端业务结果分别报告，不把局部样本正确率当成整体准确率。参考答案不得作为模型输入。


## 2026-10-28 实施与证据边界

主线已接入以下最小修改，真实前端验证进行中：

- 已恢复且同原件绑定的业务根定义在原子识别前作为精简参考提供，并进入新旧节点的关系比较。完整已核基线保留原有无模型快路；部分定义确认不等于原文任务的条件、分支和范围已完整处理，不能据此跳过整项任务。
- 变量候选与来源核对、派生答案、人工明确认定的编辑说明分开。`same_fact` 的确定类型、值域、单位、父级或已核定义冲突降为待核关系；类型相容也不证明语义相同。
- 现有 JSON 请求协议增加按需读取当前原件成员、scope、guidance、condition 和短检索。最多两轮补充取证；每轮最多四项完整证据、24,000 字符。短预览只用于导航，范围和引文重新对照当前原件及分析身份。
- 补证携带前一轮精简草稿并累积完整结果；空回复不能删除已有候选、分支、范围或未决说明。非空核心冲突保留旧项并明确待核。已有补核记录在后续运行中保留，不能因模型返回空未决清单而消失。
- 不引入通用 agent 框架，不把全部原文、完整图谱和冗余运行字段塞回每次请求。原始任务输入只存一份，补证轮记录补充内容、原始回复和实际输入哈希。

资产复核没有找到历史 79 定义／45 链的完整结构化资产。现存 novel01 人工草稿和 BQ 一变量跨项目例子均为部分核对状态；PDF SCC 参考也未成为完整可执行基线。固定目录和清理绑定不应被升级为完整图谱。资产明细留在 D 盘 `.local/drafting-harness-20261027/baseline-assets-and-residual-routing-20261028.md`，不作为发布源文件。

源码检查、构建、真实模型调用、原文质量与前端业务结果分别记录。依用户要求，产品验证通过内置浏览器触发，不使用产品 API 或命令行代替验收；新增测试源码尚未执行。暂不声明全量正确率、完整基线免识别或端到端交付已通过。

## 2026-10-28 已批准的分组与并发实施

用户在查看实测及第一方经验后明确要求“按照你的调查来实施，然后测试效果”。实施优先级为：真正已核的同版基线复用、围绕业务影响链组织识别、增量检查关系、独立组受控并发。研究依据见[分组编排调查](../research/drafting-graph-batching-primary-sources-20261028.md)。当前旧串行任务保留作对照，不中断或改写其原始结果。

- 原 OER task/observation 覆盖清单保留；分组是工作单元，不能把读过一组等同于其中所有事实、条件和范围均已完整。一个 observation 可支持多项义务。
- 已核根及明确的 OER 指导／范围关系优先组织上下文；主题、名称、成员集合相同只能作候选线索，不能自动证明同一事实。未归属和未决项继续显示。
- 一个组可跨本次选定版次的多个来源，共享业务根只输出一次；每条事实依据和修改范围仍显式归属自己的原始 task/source。组内必要前提不被共同根吞掉，尤其 BQ 格式与双信封独立，屋面与避火层独立。
- 同组补证顺序进行，独立组先限定两路；每个 worker 固定本轮模型配置，预算原子预留，单协调器持久化回执和图谱。未知发送不自动重放，旧 manifest 不因升级静默重分组。
- 原文和长响应存一份，子任务保留引用和结构结果；已有正确结果、范围和未决状态不被空回复、压缩或并发返回顺序抹去。跨组核对同时覆盖显式疑点与已核基线要求但当前缺失的边。
- 验证同一原件、版次和模型配置下的实际调用数、输入输出量、页面总耗时、重复业务根、错误合并、条件／范围遗漏，以及人工纠正次数。先分组再测并发，不能把构建或节点数下降作为准确率提高的证明。
