# OER 按需提供业务依据：统一接口与实现约束

状态：2026-10-22 用户明确要求的现行 spec，实施中，尚未验收。本文约束 Drafting、Vetting、Advisory 及公共来源实现；不把已有资源热修当作本 spec 已全部实现。

当前收口顺序：用户进一步要求尽快完成当前修复，随后亲自手动测试，发现的问题再热修。因此先收口本批公共读取及 Advisory 生产接线、必要回归和可运行版本；不继续扩大为一次性完成全部历史绑定迁移、compact frame 和 Drafting 全面重构。下面尚未完成的架构要求继续保留，不能据此宣称三模块已全部按需化。

## 目标与责任

业务需要什么，就向公共 OER／RAG 请求什么。来源解析、原文与结构的保存、修订核验、切块、embedding、索引、检索、rerank 和来源上下文装配只维护一份公共能力。三个业务模块负责业务问题、授权范围、人工决定、结果组织和显示，不分别实现来源处理管线。

OER 返回可用的完整相关依据：命中的来源单元、必要父级／条件／续段／表格／附属关系、原件位置、版本身份、已知限制和 unknown。单个短 chunk 或相邻固定字符不能冒充完整业务上下文；正文顺序不能被猜成正式条号。

“按需”包含语义检索、明确位置读取、结构化内容选择和完整范围遍历。整套审查、项目名／合约编号一致性、模板变量全面发现必须遍历声明范围，不能只用 topK 搜索后声称全套检查完成。遍历和来源关系装配仍由公共层提供。

## 公共模块与接口

### 解析进度与刷新恢复（2026-10-23 用户手测补充）

2026-10-23 后继纠偏：SPA 内切换模块或项目，不得销毁已明确启动的上传队列；工作必须继续绑定启动时的项目，逐文件等待回执及来源刷新后推进。队列与本地 File 引用由公共前端模块维护，页面仅订阅当前项目状态。整页刷新／关闭浏览器与模块切换分别处理：浏览器本地文件引用丢失后只恢复记录和服务端状态，不自动重传；不得仅按同名文件认定某次请求已收到回执。已丢失的旧队列不能凭数字伪造恢复。

Drafting 初始读取也应按需：文件目录先展示，恢复已完成任务时只读取一次当前核对版本，不能再次下载历史结果图并重跑整个读取链。文件页不提前计算采用／导出计划；进入相关步骤再读取，并在来源刷新时使旧计划失效。目录查询只读展示字段，图谱来源先按业务类别筛选；同次文稿列表的渲染配方核查可复用，跨请求仍重新核验。不得用省略原件／版本校验来换取速度。

Vetting 上传进度须区分浏览器收到的处理回执、服务端文件解析状态和来源质量。浏览器刷新只恢复当前项目队列记录并接回服务端状态，不自动重传文件、续发未发送文件或重新派发模型。刷新前尚未确认的请求显示结果未确认；历史未记录的队列和逐页进度不能事后推算。

公共解析器报告真实物理页与阶段，包含文字／结构读取、页面渲染、视觉识别等待、原生表格／版面批次及结果保存；进度沿既有来源记录保存。轮询仅查询当前来源的身份、文件名、状态、页数和处理说明，不读取或反复传输正文、结构或候选图。来源身份及解析中状态匹配后才允许写入；进度写入失败不得改变内容解析结果。完成状态应同步回文件列表，短暂读取失败继续接回。

当前本地单业务后端重启时，将遗留 Vetting 解析标明中断，保留原件和已有观察，不自动重试；多个业务后端共享数据库前须增加任务所有权／租约，不能沿用单实例启动判定。本批验证见[结果验收报告](../testing/drafting-result-usability-20261023.md)首节；普通 DOCX 双通道视觉接线仍按下文未完成状态保留。

### DOCX原生读取、派生视觉与页码状态

2026-10-22手测已确认，普通DOCX上传当前只接入POI／OOXML原生解析，没有自动转PDF、双视觉解析、三路核对或页码映射，也没有后台补跑队列。Sean项目3份模板及15份沟通资料均pageCount=0、ocrUsed=false；历史离线双视觉实验不能替代生产接线。详见[真实缺口与界面反馈](../testing/docx-upload-production-gap-20261022.md)。此项尚未实现，不以PARSED、上传成功或已有OCR服务推定完成。

公共来源准备须复用现有LibreOffice及两套完整视觉解析能力，按同一原件修订关联派生PDF、renderer／字体／配方、页级覆盖、分歧与失败。原生读取、派生视觉处理、页码映射和质量核验分别报告可用／未执行／运行／失败等实际状态；同一来源和配方供三模块复用，禁止在每个业务上传方法各建转换／OCR管线。原生编辑语义继续保留，视觉结果不自动覆盖原文；派生页不能冒称Word原件权威分页。原生已有可用内容先提供用户使用，局部视觉失败保留人工兜底和明确限制。

复用现有 `DocumentParser`、来源 registry／CAS、`CanonicalEvidenceService`、`OerBusinessEvidence`、`OerCanonicalRetrievalClient`、`retrieval_source_units.SourceUnits`、`WindowRuntime` 及已配置模型。不得另起并行 parser、chunker、上下文闭包、embedding 或 PDF 技术栈。

| 公共操作 | 请求 | 返回 | 现有入口／实施方向 |
| --- | --- | --- | --- |
| 准备来源 | 项目、允许的文件身份、原件与解析修订 | 来源地址、版本 pins、状态与完整性限制 | 复用上传／`NormalObservedPreparationService`／registry；同一内容修订和配方不反复构造或封存 |
| 建立／检查索引 | 允许的来源地址、module、模型与配方 | compact 索引 receipt、覆盖范围、状态 | 保留 `/index-canonical` 与 `/index-canonical/status`，不向业务要求完整候选图 |
| 语义检索 | 项目／module、来源范围、问题、必要过滤与结果预算 | ranked hits 及公共来源单元闭包 | 保留 `/retrieve`，不另建一种检索算法 |
| 来源目录 | 来源地址及当前 pins | 来源身份、数量、质量／覆盖声明、修订 identity；不含正文与完整图 | 公共 `/sources/read` 的 `catalog` 操作 |
| 指定依据读取 | 同范围内的明确 chunk／origin IDs、预算 | 请求顺序对应的完整相关来源单元及其 members／定位／unknown | 同一 `/sources/read` 的 `ids` 操作，复用生产 `SourceUnits.resolve`；不在 Java 业务模块重算闭包 |
| 完整范围遍历 | 同范围 pins、稳定 cursor、数量／字节预算 | 有序完整来源单元、next cursor、覆盖／未执行状态 | 同一 `/sources/read` 的 `scan` 操作；cursor 必须绑定来源修订和实际顺序 |

`/sources/read` 是同一来源读取能力的有限操作，不承接任意 Python、SQL、文件路径或自由规则。明确 ID、稳定顺序和公共来源结构是它的输入；法律采用与合同业务判断仍由业务层处理。

生产按需入口必须在 health 宣告实际能力及版本。缺少该能力时返回明确的未就绪状态，不静默回退成业务端下载整图、本地重切块或换模型。独立实验脚本和旧 prototype 不得作为新公共入口的基础。

## 来源身份与信任边界

每次请求绑定项目、module、实际授权来源集合、原件 SHA、解析修订、projection／来源修订及索引／配方身份。权限、模板用途、NSC／BSSSC 与人工采用状态不得因内容复用而合并。图纸保持识别后排除，评价资料保持隔离。

公共层在入站与出站重新检查实际 CAS、来源修订及软件／配方身份；Java 重新检查当前数据库、原件与授权范围。业务只接收 compact 身份及该次需要的来源内容。禁止要求 Java 为每次查询重复传输、解析完整封存，只为再次证明同一份已由 OER 验证的结构。

来源／模型／tokenizer／预处理／配方改变必须失效。可复用同一阶段验证结果及不变的派生内容，不能用缓存、文件大小或 mtime 代替实际字节核验。共享 embedding 必须绑定完整模型输入与模型配方；业务权限和索引视图分别核验。

普通 parser observation、reviewed adoption、人工确认和 unknown 分别保留。跨模块 reviewed 权威按既有契约处理，外模块 normal 不能升级为共享审定事实。坏的新修订不得回退旧修订后冒充当前。

## 数据所有权与资源约束

完整来源图、原文、解析结构及 CAS 证明由公共来源层持有。业务保存地址、compact pins、必要结果与人工状态，不为每个业务模块再封存完整同义副本。业务调用不能以 `load complete snapshot → reconstruct complete graph → locally filter` 实现普通按需读取。

目录、状态、存在性查询不得读取正文／候选图／PDF LOB。当前修订选择按顺序有界读取，选中后停止，不预加载全部历史修订。索引状态、查询及来源目录不因为只问一个状态就生成完整业务 corpus。

有界批量请求不能暗中截断一个完整来源单元。完整表格或条件组超出预算时，返回明确的过大／未完成状态、位置及可继续方式；不得用缺失尾部的内容授予 complete。必须保留已取得的可用内容及人工兜底，不能因局部缺值或模型 JSON 问题让整份 Drafting 无结果。

同一修订／同一配方的重复准备与进行中任务应共用公共结果。重型来源处理串行或受既有整机预算约束；不得通过不断加堆掩盖数据放大。Java 验证仍按 32 GiB 单 worker 和资源守卫；业务堆保留用户要求的 64 GiB，但堆上限不等于整机预算。

## 三模块消费方式

### Drafting

- 模板结构发现保留 `OerTemplateEvidence` 的指导语、marker、groups、conditions、sourceMembers、named text channels 与原生编辑目标位置。公共读取须支持明确 observation ID 及完整关系闭包；普通 canonical chunk 不是这些观察的等价替代，未映射部分必须列明 unsupported／unknown，不能静默省略。
- 模板发现通过公共结构遍历取得完整编制要求；项目值提取按已审核变量请求相关项目资料及必要上下文，不能自己固定每 3000 字再补邻域／表格关系。
- 模板发现使用现有 `OerTemplateEvidence` 的 observation：guidanceNotes、markerCandidates、groups、conditions、sourceMembers、named text channels 与 native 位置。它不是普通 canonical chunks 的同义物。公共入口须按 observation ID 返回该项及完整条件／指导语／编辑目标关系；不能用普通 topK 文本替换后漏掉编制要求。编辑坐标仍由 `DraftReviewSources.bind`／`DocxTemplateEditor` 验真。
- 原件、模板版式及编辑目标仍使用原生 Word／现有 LibreOffice。生成和导出需要原件字节属于明确的文件操作，不通过 RAG 重建 DOCX。
- 项目名／合约编号的顶级变量、确认替换及贯穿项目包、人工兜底和两种安排下的 BS 工种选择保持既有产品要求。

### Vetting

- 2026-10-22用户再次确认：Vetting主流程审查已经拟好的文件包，检查错漏、矛盾、不合规并输出可复核报告；收集项目事实、识别变量、填值和编制文件属于Drafting主流程。Vetting不要求用户先按招标文件／项目事实／标准／目录分批指定语料角色，也不把补齐Drafting资料作为开始审查的前置条件。
- 上传入口默认交公共身份路由识别，移除整批“上传文件用途”选择。内部保留待审对象和适用依据的来源角色，不能因简化UI把全部文件强制标为tender；判断不明时，仅对具体文件提供带来源身份约束的确认／纠错。不会自动采用Drafting变量或把Drafting的原始输入当作本次已拟好的待审包。

- 对完整审查范围调用公共有序遍历，覆盖台账记录已执行、失败、unknown 与未执行部分；不能仅凭语义召回数量给出全部无问题结论。
- 项目身份、正文／页眉页脚等结构化依据由公共层选择与定位；审查规则不再分别解析来源结构或重建上下文。
- 报告与最终 Word／PDF 复用现有公共渲染，业务报告版式和人工核对状态不混入来源事实。

### 2026-10-23 Vetting：语义审查与按需取证的实施设计

状态：round378设计经round379结合实际caller再审，round380已接入Vetting并随review102联合部署，启动、只读HTTP及所选业务数据保全回验通过；真实来源性能及语义业务验收仍未完成。具体实现、收据与成本边界见[本轮修复记录](../testing/vetting-semantic-demand-hotfix-20261023.md)。以下是实施约束，不是本轮审查通过的证明。不新增一套解析、检索、证据存储或报告体系，不默认增加第二轮LLM，也不为每条候选增加人工放行步骤。

#### 已查明的问题与数据边界

- 项目PRE在范围内，与被排除的SL Preliminaries参考库不同。当前source101已有原生文字，实际状态仍为PARTIAL；其说明为“DOCX已解析10930个段落/表格/页眉页脚/脚注尾注位置；未推算页码”。身份记录却仍为UNKNOWN、角色为空、用途unknown，故以`source_identity_unresolved`未进入本轮。不是PRE类别应被排除，也不是已经确认它属于SL PRE。
- 既存正文开头已有`PRE.B1 PROJECT PARTICULARS`等目录线索；现行身份记录未保留据此确认的原生标题证据，只有文件名候选。本轮未重放路由，不把目录／标题漏接的静态分析冒称动态分支取证。后继须用同原件的可验证文字及结构修正公共路由，不能仅按文件名或`PRE`字样强行授予身份。
- “原生文字已读取”“身份／用途已确定”“版面／覆盖核验状态”“已纳入本次审查”是不同状态。文件列表不能用一条“已解析”掩盖后三者；待定来源必须在本轮覆盖说明中显示具体原因和确认入口，不能静默消失。
- 已证实Java先查询项目全量business大字段、后执行来源筛选；排除的PRE四个文本字段合计713,610,314字符也处于该读取路径。该数字是数据库字符长度，不是LLM请求字节，更不证明整份PRE发给了LLM。已有模型投影仍携带部分结构、位置及来源校验元数据，需继续收口；本地读取与实际模型消息分别测量。
- 本轮第一包的既有probe确认：model user字符串为1,413,221个UTF-8字节，完整Input序列化为1,565,359字节，二者的user message逐字一致。Source excerpts占user字符串1,350,739字节，包含原文及结构，不把这个比例误称为全部元数据。无损展开后结构中仍有大批Word布局／XML位置字段；未见整份PRE、Annex的数据库LOB、原件blob或完整原始OCR响应。probe字符串不是独立抓取的HTTP实体，实际线上字节数尚未测量。

| 候选取证与机械校验 | 用候选引用编号及精确引文调用已有ids读取和证据门，核对来源身份／权限／版本、引文及所声明对照成员；只执行有明确定义的确定性规则 | 默认无新增模型调用；新补出的必要正文、条件或相反约定在原输入中缺失时，原判断保持未决，在既有预算内补读并重新判断 | 保存与本包绑定的可复核证据；机械通过不等于语义或法律正确。来源或引文不符拒绝该候选，保留失败及unknown，不猜坐标，不重载整个来源图 |
| 人工核对／原件显示／报告 | 用户打开具体意见才加载关联原件与高亮；导出按已验证意见批量解析所需位置 | 无定位专用LLM调用 | 复用现有原件预览、引用、核对记录、checkpoint与报告快照；人工决定独立保存，未覆盖及失败仍明确显示 |

这里的“先确认再取解析字段”首先指系统完成候选判断后，按引用找回相关证据并验证；人工最终核对仍在原有报告流程，不要求用户逐条点击才能让后台继续。判定所需的定义、例外、表头、续段或交叉引用必须在正式结论前取得，不能为了让第一轮变小而故意省掉这些语义条件。补齐已知必要上下文不能以“模型已经发现问题”为触发前提，否则缺失上下文造成的漏报没有补救入口。完整表格／条件组超过预算时继续沿公共有界读取处理或标未完成，不硬截断。

普通语义提示词不要求模型还原原始解析JSON或解码来源审计字典。短编号只承担引用，不要求模型理解hash、CAS地址或坐标变换。表格的行列归属、单位、合并单元格范围及脚注等若改变语义，公共层应给出经来源绑定的必要表示；不能删除这些信息后把歧义判成一致。问题本身依赖可见样式、表单选择或版面关系时，按该具体问题补充相关观测及限制，不因此把全包几何和原始provider记录交给所有主题。

**语义判断不能交给引文校验替代。** 两条引文都真实存在，仍可能分别约束不同分包商或不同阶段。现有`VettingSemanticReview`证据门只声明`mechanically_accepted`，`semanticQualityAccepted`仍为null；`VettingChecklistRequirementRelations`也明确原生位置不证明字段角色、同一对象或法律意图。收紧输入必须保留这一区别：不能把后端比较两段字符串设计成通用的主体／条件／适用性裁判，也不把第二次LLM自审当成独立验收。

**短引用贯通输入、输出和保存。** 每包建立不可变映射：短编号对应该包来源修订、单元／成员及实际提交文字；引用只允许回到本包已经提交的范围。LLM返回短编号、准确引文和业务说明，必要时指明已展示的成员编号；后端解析原生位置、UTF-16区间和PDF坐标。当前schema的`support.facts.nativePositionIndex/startUtf16/endUtf16`与`VettingChecklistRequirementRelations.bindFact`依赖模型提供原生数组索引，必须连同prompt、解码、机械校验及契约测试一起改接，不能只删输入字段或把support一律置空。引文重复时保留候选位置或要求更明确的成员引用，不按第一处命中猜位置。来源单元和引文已核实但物理页／高亮尚缺时，可显示带定位限制的候选；来源本身无法绑定时保留待核记录，不能发布为已核证据。现有人工记录与旧报告按其原协议继续读取，不重写历史。

#### 用现有实现收口

1. **先筛选，再加载。** `SourceDocumentRepository`／`VettingService.sourceSet`改为先读取当前目录的身份、权限、修订及状态字段并完成范围选择，再按选中的ID取得实际需要的正文／来源单元。待定及范围外文件保留在覆盖目录，但不进入内容加载。新修订即使失败也不能回退旧版冒充当前。身份识别修复和旧记录纠正分别执行，不直接修改正在运行任务的冻结范围。
2. **公共读取不绕回整图。** 沿现有`/sources/read`的catalog／ids／scan及`OerCanonicalRetrievalClient.readSources`改接`OerBusinessEvidence.loadSession`与guard，不能在调用ids前先下载完整snapshot。`source_read_server.py`当前每次请求仍`registry.load`完整来源并汇集全部chunks，catalog的轻量响应不是内部轻量读取；Java改接不能只把开销搬到Python。复用既有来源manifest／批次和地址，在同一读取接口提供语义视图，按需返回正文、必要关系、限制及证据地址，重型定位／原始观察仅在需要时取。新view与能力版本须明确宣告，不能假称现行仅支持`canonical_units`的v1已实现。normal Word现有`wordSourceScopeContext`／`selectedWordScopes`闭包继续复用或等价下沉；缺失能力显示unknown，不能用普通chunk替代后宣称完整。
3. **收紧现有模型投影及引用输出。** 在`OerModelMaterial`／`VettingSourceMaterial`现有入口按语义用途选择字段，连同现有输出schema／解码／证据绑定改接上述短引用；同包同一单元正文只展示一次，用短编号表达其它关系。实际机器验证需要的hash、定位及原始观察在证据侧核验，不因不再送入提示词而失去验证。不得新增平行chunker、关系闭包算法或另一套证据DTO全图。
4. **同次校验共享，不缓存有效性结论。** 目录筛选和来源现状检查不能加载全项目内容LOB；公共读取仍保留实际原件、已用CAS、修订／权限和软件身份的入站、出站校验。同一请求私有frame共享已核验的纯重构结果，退出守卫成功后才发布结果。跨请求重新核验实际字节；不得以mtime／大小、可写mmap未改stat或数据库中旧SHA代替当前字节检查。
5. **相同实际输入不重复付费预检。** 现有prepared request应在最终消息、schema与生成预算确定后封存一次，在同一操作内复用与该实际输入、模型／tokenizer／配方、来源pins及输出预算绑定的有效usage观察。planner与final不能仅因阶段名称不同，对相同请求再次做cap1生成；修复提示词或实际输入／预算改变则重新检查。只复用成功取得并通过校验的观察，超预算仍拒绝生成，超时／取消／结果未知不能变成许可；命中时不再占一次付费调用额度，但实际回答仍按既有ledger计数。每次使用仍核取消、动作期限、模型配置及来源现状，不跨操作／provider复用，不把本地估数冒充实测供应商用量。
6. **进度分开计。** 沿既有任务记录报告准备范围、读取依据、预检、模型判断、补证／重试和保存阶段，显示当前主题、阶段耗时以及已保存／失败／未完成数。失败不得显示成成功数，`语义审查6/17`不得被表达成六项审查通过。进度查询只读小字段，不触发来源准备或模型调用。

**扫描覆盖与审查覆盖分开。** 公共scan证明声明范围内哪些来源单元已经读取；现有packet／source-request台账另外记录“检查事项—适用单元／对照组”的计划、实际提交、返回、机械接受和人工复核。读取一遍或返回空数组不能升级整包checked-pass；NA需要范围依据，无法判断适用的单元保持待核。基础审查必须覆盖可用声明范围，现有主题检索用于补充和排序，不能让topK未命中的正文消失。相关检查可同包执行，不机械地把所有正文向17个主题各发一遍。

**跨文件比较必须联合提交。** 复用现有`VettingContextBuilder`、source-request及token-aware组包中的引用／条件／比较关系，用公共ids／retrieve取得对侧及必要限定；基础遍历或已有关系发现的跨文件线索进入同一执行台账，不另建全包实体图或两两笛卡尔积。NTT要求电子递交、SCT要求纸质递交的两侧若落入不同包，两包各自完成不证明已经比较。两侧及条件在同包接受判断，或该对照保持未完成；检索关联只产生待比较线索，不能证明同一事项。已知关系执行完也不证明所有潜在语义关系均已发现，漏报仍须独立质量验证。目录／附录“未列载”等否定结论必须有相应完整文字范围的检查证据；未上传或未解析的内容应报无法判断，不能报已证缺件。未提供、身份待定、解析未完成、未提交模型、模型失败、证据不足和已核无问题分别记录。

“默认不增加第二轮”指每个语义依据充分的审查包不例行再发一次模型自审，不表示整项任务只有一次请求。基础包、跨文件对照包和必要补读共用原有总调用／修复／时间预算，达到上限保留未完成清单，不为追求全覆盖无限循环或静默扩大预算。

#### 分批实现与必要验收

先修目录筛选及PRE身份／展示接缝，再贯通公共内部有界读取、语义视图与引用输出，补齐基础遍历／联合比较的执行台账，收口重复预检和阶段进度；保留原有意见、人工记录、checkpoint、版本及报告快照。每批记录代码／契约与真实运行差别，不以文档更新声明性能已修复。旧完整封存可能使首次读取仍昂贵，须单列冷读及未改接路径，不能用新视图的小响应声称全链路已按需。全量历史binding迁移不是本次设计自动授权的数据库操作。

- 目录、进度、身份待定状态展示及仅目录资格筛选断言零正文／完整解析LOB读取、零模型调用；被排除的巨型PRE不能放大其他选中来源的加载量。身份识别／纠正按需读取既存身份观察或有界原生标题等必要证据，不因未知身份预加载整个来源图或重跑整份OCR；额外模型执行按独立任务授权处理。
- 同一原件项目PRE在验证标题和身份后能纳入；SL PRE、图纸、计价文件和评价资料继续按既有范围隔离。UNKNOWN不靠文件名转成tender，旧冻结任务不被原地换源。
- 实际模型消息逐项检查允许字段与体积；普通语义输入没有整图、原始OCR数组、CAS／审计收据、无关几何或样式。必要原文、表头／单位、例外、续段、引用和版本限制逐项与来源等价，不以删语义换体积。
- 完整scan的origin无遗漏／重复，必要闭包成员可在不同包重复；另核实际检查与联合比较台账。有相关问题但topK未命中、两侧被分到不同包、跨页表头／例外、引用目标缺失、局部来源不足、模型空结果或只返回一条consistent，均不能误授全包无问题。包含真实冲突及不同主体／条件下合理差异的独立质量对照，代码／fixture通过不代替模型判断正确。
- 不默认追加模型自审；必要补读仍受既有总预算限制。相同最终输入只做一次付费预检，输入变化必须重新检查；动作过期、取消、预检失败／结果未知不能凭复用绕过。调用次数、实际输入token和缓存指标分别留证，不把缺失缓存指标当作未命中。
- 短引用从实际模型消息到schema／解码／原件定位／checkpoint／报告端到端一致；测试多处相同引文、跨成员引文、非BMP字符和旧报告读取，不依赖模型猜原生数组索引。物理高亮缺失与来源绑定失败分开，不能把可靠候选全丢或猜第一处位置。
- 来源／授权／修订、同大小同mtime的实际原件或CAS变更、越界引用等负控继续拒绝；每项机械通过保持非语义验收身份，人工决定不自动产生。
- 通过前端验证解析阶段与审查准入分开显示、失败数持续可见、刷新后阶段恢复、点击意见按需打开正确原件，人工未保存状态保持。
- 在同源／同模型／同范围下分开记录DB字段读取次数／字符量、OER内部加载／反序列化、OER响应字节、模型消息字节／token以及原件／CAS校验读取；不能把数据库字符数当传输字节，也不能把全图读取搬到Python后记为消除。分别计冷／热准备、读取／构造、预检、回答、补证、保存和整轮时间；没有实际新任务验收前不承诺速度倍数。源码／fixture通过不能替代真实LLM、原件质量及业务验收。

### Advisory

- normal Word 的既有 `selectedWordScopes`／`wordSourceScopeContext` 契约包含正式归属边界、条件／指导语／续段／分支。公共层继续复用这一现有能力，或完成同源下沉并作逐项等价验证；仅 `SourceUnits.resolve` 当前不足以替代，不得以新读取入口掩盖缺失上下文。
- 按问题使用 `/retrieve`，按引用或后续补问使用明确 ID 读取；表格补全、条件／续段和适用文件关系调用公共来源读取。
- 删除业务端扫描全 corpus 后自行补表格、按文件名寻找采用上下文等来源处理分支；法律适用性判断及资料不足表述仍由咨询模块负责。
- 保存会话、历史引用与原件定位绑定当时的来源修订，不把同名新版替换旧引用。

## 验收与防回退

1. 三模块的生产调用确实通过上述公共接口；测试、兼容入口或未接 caller 的新类不算实现完成。
2. 对固定来源，证明 catalog／status 不传正文或完整 snapshot；指定 ID 请求只返回该单元及必要闭包。用调用计数和响应大小断言阻止回退成整文读取。
3. 全范围 scan 按同一修订的顺序无遗漏／无重复，结束时有完整覆盖台账；部分失败与未执行不能算通过。目录／cursor／顺序／来源变化均有负控。
4. Word／PDF／normal／collection／family 的来源单元保留原文、定位、条件、表格、续段与 unknown；Java 与 Python 不维护两套生产闭包算法。保留旧新完整输出对照。
   当前 normal Word 的 `wordSourceScopeContext`／`selectedWordScopes` 仍承担完整条件／指导语／续段范围补全，Python `SourceUnits.resolve` 尚未等价覆盖。实现必须复用／下沉这份既有契约，或明确声明尚不支持并保留 unknown，不能默认切换后声称上下文完整。迁移不能以删除现有范围证据来减少体积。
5. 跨项目、module、用途、来源变更、CAS 字节变更、软件／索引 recipe 变化、错误或越界 ID 必须被拒绝；不能用旧 cache 成功结果遮蔽这些变更。
6. 同一来源重复消费不会在三个模块各重新解析／切块／嵌入；实际模型输入相同且配方相同的复用单独计数，不能将不同权限索引强行合并。
7. 有架构契约检查阻止业务重新引入本地切块、完整封存解析及闭包装配。原件编辑／导出等允许的全文操作逐项列明，不能以一条宽泛例外放过全部业务源码。
8. 软件契约、真实服务调用、来源质量、实际模型、前端业务和最终文件验收分别报告。当前资源热修的绿色测试不替代本 spec 的三模块按需验收。

实施顺序：先收口已修改的资源热修，再在既有 OER 增加公共 catalog／指定 ID／scan 读取及对应真实 HTTP 契约，接同一 Java 公共消费入口，逐模块替换并删除旧生产旁路，最后完成真实资料与前端闭环。不得只新增文档或孤立接口后宣称目标完成。
