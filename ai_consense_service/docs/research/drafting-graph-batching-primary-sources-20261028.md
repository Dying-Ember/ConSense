# Drafting: fixed-graph grouping, bounded concurrency and evidence reuse

Research date: 2026-10-28. Scope: first-party engineering guidance and a read-only review of the current Drafting orchestration. This note proposes an experiment; it does not report a model run, speed improvement, accuracy result or frontend acceptance. No product API, model call or service operation was performed for this research.

The recommended direction is **reuse a verified same-edition graph first; group the remaining work by business root and its dependent branches; run independent groups concurrently; preserve group-local evidence and progress; reconcile only cross-group questions afterward**. This is an application design inference, not a vendor claim that a particular concurrency level will improve Qwen 27B.

## Five conclusions supported by primary sources

### 1. Use a predefined workflow for known graph structure; reserve model planning for genuinely unknown differences

Anthropic distinguishes workflows with predefined execution paths from agents that choose their own path. It recommends the simplest sufficient design. Its orchestrator-worker pattern is intended for cases where the required subtasks cannot be predicted in advance. A known fixed-variable graph therefore supports a simpler starting point than asking a model to rediscover the task decomposition for every note. [Anthropic, Building effective agents](https://www.anthropic.com/research/building-effective-agents)

**Drafting application proposal:** identify the source edition, recover the reviewed baseline, and create one task per relevant business-root group. The worker receives the root meaning, value domain, dependent conditions and the current source passages that support or differ from that group. It returns differences and uncertainties, rather than recreating every known definition. Newly encountered requirements that cannot be assigned safely go to a separate unresolved queue. A group assignment is a working hypothesis until source and definition checks support it.

**Boundary:** identical wording or a matching clause number is not sufficient edition identity. The two SCC clause editions must stay separate even if one arrives as DOCX and the other as PDF. This is an existing project requirement, not a conclusion supplied by the vendor article. A partially recovered baseline cannot be promoted to a complete executable graph by this scheduling change.

### 2. Parallelize independent groups; keep a root and its alternatives together

Anthropic describes task sectioning as parallel execution of independent subtasks. LangGraph similarly distinguishes predefined parallel workflows from dynamic orchestrator-worker planning; its workers have their own state, with results collected for synthesis. These sources support parallel isolation and controlled aggregation, not uncontrolled concurrent mutation of a shared graph. [Anthropic, Building effective agents](https://www.anthropic.com/research/building-effective-agents); [LangGraph, Workflows and agents](https://docs.langchain.com/oss/python/langgraph/workflows-agents)

**Drafting application proposal:** electronic versus paper submission and its Alternative A/B consequences belong to one group because their meaning depends on the same root choice. The group can span NTT/SCT/SCC passages within the selected editions. An independent warranty group may run concurrently. Each worker publishes a proposal against the same immutable baseline revision. A single deterministic merge step retains source ownership, detects duplicate candidates and collects disputed cross-group edges. Only unresolved cross-group meaning should need a later model pass.

Grouping must preserve an explicit mapping from every original source observation to its assigned group and processing outcome. It changes the unit of scheduling, not the coverage denominator: the original source inventory is still the completeness ledger, including unassigned and unresolved observations. A small number of completed groups cannot stand in for complete source coverage. Cross-group dependencies use stable, read-only root IDs and are scheduled in dependency layers; do not expand each group into an entire connected component until the whole template becomes one large packet. These are proposed controls for this product, derived from the independent-worker and shared-state pattern rather than a claim that LangGraph verifies drafting coverage. [LangGraph, Workflows and agents](https://docs.langchain.com/oss/python/langgraph/workflows-agents)

One source observation may support obligations in several groups: the mapping is not one-to-one. In the BQ example, the issue-format choice does not determine the independent two-envelope premise or every submission-medium requirement. Roof and refuge-floor waterproofing likewise remain independently answerable facts even when one guidance paragraph mentions both. The final cross-group check must include baseline-required edges or obligations that are absent from the result, as well as conflicts that the model explicitly reported; silence is not evidence that no edge is missing. These are product-specific counterexamples, not vendor claims.

Start an experiment with concurrency 2, then consider 4 only if observed latency and provider capacity support it. These numbers are proposed experimental settings, not measured optima. Concurrency alone reduces neither the number of calls nor the sum of input tokens; grouping and reuse must do that work. A locally saturated model server may queue concurrent requests, so no speed ratio is promised. Anthropic's research-system article also notes coordination costs and that shared-context, tightly dependent work fits multi-agent execution poorly. Its results on its own research system must not be transferred to this deployment. [Anthropic, How we built our multi-agent research system](https://www.anthropic.com/research/multi-agent-research-system)

Alibaba Cloud's official guidance separates request/token limits per minute and second and also describes traffic-burst limits. It recommends smoothing traffic rather than relying only on retrying errors. For this experiment, bound both active calls and estimated token demand, ramp up gradually, and retain the actual rate-limit reason. The deployed `qwen3.8-27b` endpoint and account limits have not been matched to those Model Studio features here; do not import a published quota or assume automatic retry is safe for an UNKNOWN paid dispatch. [Alibaba Cloud, Best practices for handling rate limiting](https://www.alibabacloud.com/help/en/model-studio/rate-limiting-best-practices)

### 3. Reuse completed application work and persist each useful result before considering provider prompt caching

LangGraph supports node-result caching keyed by node input. Its checkpoint documentation describes retaining successful task writes when another parallel task fails. Its graph documentation warns that resuming a node can rerun earlier effects, and recommends idempotency and persisted task results. [LangGraph, Graph API: node caching and re-execution](https://docs.langchain.com/oss/python/langgraph/graph-api); [LangGraph, Checkpointers](https://docs.langchain.com/oss/python/langgraph/checkpointers)

**Drafting application proposal:** use the existing run/item/receipt infrastructure. A reusable group result needs a key covering the exact source edition and analysis identity, relevant baseline-definition fingerprint, group evidence identities/content, prompt and output-schema version, and model/configuration identity. Only a change in these inputs invalidates the group. Do not include unrelated graph events or project answers in a template-definition cache key. Do not cache a timeout, unknown dispatch outcome or incomplete result as a successful conclusion.

Persist a valid model response and the next evidence request after each useful round, so a crash does not require repeating all previous supplementation for that group. Preserve the existing distinction between PENDING, completed and UNKNOWN calls. A local dispatch record cannot prove whether a provider completed a lost request; do not silently resend such a request as though it were never issued. These are proposed application safeguards, not an assertion that a framework guarantees exactly-once paid inference.

Provider prompt caching is a different mechanism: Anthropic's documented facility caches matching prompt prefixes through its own API controls and expiry rules. It does not establish support in the current Qwen gateway. An application result cache avoids a call; prefix caching, when supported, still requires model inference. Adopt neither Claude-specific cache parameters nor an assumed cache hit rate here. [Claude Platform, Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)

Alibaba Cloud likewise documents caching common input prefixes for supported models, and explicitly states that an implicit cache hit is not guaranteed even for identical context. Stable system/schema/definition prefixes are therefore a possible secondary optimization, but neither the model name nor a reused session label proves a hit. The actual Qwen endpoint's support and returned usage fields remain unverified. Measure provider-reported cached input tokens if available; do not claim result reuse, free inference or unchanged accuracy from an assumed prefix-cache benefit. [Alibaba Cloud, Context Cache](https://www.alibabacloud.com/help/en/model-studio/context-cache)

### 4. Maintain compact group state and request missing evidence through the existing JSON protocol

Anthropic recommends relevant, compact context and a hybrid of prepared context plus on-demand retrieval. It describes compaction and structured notes for long tasks, while warning that aggressive summarization can lose important details. Its tool-design guidance favors meaningful responses and explicit controls over response detail; tool usage should be evaluated from actual traces. [Anthropic, Effective context engineering for AI agents](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents); [Anthropic, Writing effective tools for AI agents](https://www.anthropic.com/research/writing-tools-for-agents)

**Drafting application proposal:** preload the relevant fixed root definition and source-backed branch outline. Keep a small group state containing stable local node IDs, proposed meanings, branch and effect references, completed decisions, conflicts, and remaining evidence needs. The model can emit the existing `sourceContextRequests` and `sourceSearchRequests`; the harness resolves them against saved current-source evidence and sends the resulting evidence back in a follow-up JSON round. This realizes a tool loop without assuming native function calling.

Deduplicate evidence requests by source/analysis identity plus observation kind and ID. A source search preview remains a navigation aid; full source evidence is required before it supports an accepted claim or range. Within a group conversation, avoid resending the entire transcript and repeated large observations when a compact state plus necessary current evidence suffices. After a context reset, an ID alone does not teach the new model the passage: rehydrate the evidence needed for its next decision. Store complete originals and accepted graph records outside the conversation; a free-form summary must not replace those records.

**Boundary:** merely calling multiple stateless completions the same “session” does not create provider memory or prefix caching. Tool loops can themselves add latency. The first packet should include obvious relevant evidence; incremental disclosure is for missing details, not a reason to force a separate request for every sentence. Large context capacity is not proof that filling it improves this task. [Anthropic, Effective context engineering for AI agents](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)

### 5. Judge both the resulting graph and the human correction cost; fewer calls are not an accuracy result

Anthropic distinguishes the agent's transcript from the actual final state, recommends suitable code/model/human graders, and separates capability evaluation from regression evaluation. It also discusses repeated-trial consistency: one successful run is insufficient evidence of reliability. [Anthropic, Demystifying evals for AI agents](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

**Drafting application proposal:** compare the current workflow against grouped serial execution and grouped bounded concurrency using the same source originals, selected SCC edition, fixed graph version, Qwen model/configuration and task boundary. Capture the graph before manual corrections. Measure the following separately:

| Question | Evidence to retain |
| --- | --- |
| Did grouping reduce repeated work? | Actual dispatch count; repeated same-input dispatches; input/output tokens when reported; cache-hit provenance; supplementation rounds |
| Did it become faster? | Frontend start-to-reviewable-graph elapsed time, provider wait, local preparation and merge time; cold/warm conditions stated |
| Did semantics improve? | Root-variable precision/recall; correct fixed-definition matches; duplicate roots; wrong merges; missing alternatives; unsupported and incorrect cross-group conditions |
| Can it edit the correct content? | Per-branch source identity, complete affected-range coverage, action correctness, unresolved ranges retained; no authority inferred from a search preview |
| Did manual work shrink? | Distinct groups requiring decisions, corrective edits/merges/range repairs, explicit confirmation actions, and observed operator time |

A fixed graph is a reference only where it has been checked against that edition. Unknown PDF-SCC ranges cannot be scored as known ground truth. Model-based judging may help identify cases to inspect, but it cannot independently establish that its own graph is complete. Real runs and end-to-end acceptance remain frontend-only under the user's existing instruction; offline contract checks and research are separate evidence classes.

## Current code seams inspected, without execution

These are current working-tree observations, not claims from vendor documentation. Other agents are changing this tree, so line positions can drift.

- `DraftAutomationService.java:40`: the executor currently has one worker. `processTasks` at about line 150 processes pending tasks in a sequential loop, writes IN_FLIGHT before processing and a receipt afterward. Increasing the executor's outer thread count alone would allow multiple runs, not necessarily parallelize independent tasks inside one run.
- `DraftAutomationService.java:93–100`: interrupted in-flight items become UNKNOWN; the existing no-automatic-paid-replay behavior should survive the experiment.
- `DraftAutomationService.java:120–125`: a complete reviewed same-edition baseline already has a direct restoration path. Optimize this path before scheduling extra recognition.
- `DraftAutomaticDiscovery.java:93`: the current prompt already advertises `sourceContextRequests:[{kind:member|scope|guidance|condition,id}]` and `sourceSearchRequests:[short literal concepts]`. Use these existing JSON fields rather than inventing a native tool API dependency.
- `DraftDiscoveryEvidence.java:12–52`: the evidence adapter resolves bounded requests from current readings and marks search output as navigation-only. It already deduplicates repeated kind/ID requests within a context call; group-level reuse across rounds is a separate design opportunity, not something this inspection proves is already implemented.
- `DraftAutomaticDiscovery.java:279`: finishing starts with existing relation proposals and appends new ones. A concurrent design must keep deterministic, provenance-preserving publication and must not let workers race to overwrite the saved graph.

## Minimal experiment sequence

The current frontend-started run supplies a useful local measurement. At the 24/255 observation, 24 completed model requests occupied 432.728 of 435.973 measured seconds (99.26%); this is request-to-response time including network, provider and adapter, not GPU-only time. A read-only sample of the first 25 primary requests showed 24 scope occurrences but 11 distinct source-scopes, and 16 task pairs with identical same-source member-ID sets. None of the 25 complete user JSON inputs were identical. These facts support removing fragmented repeated reading, but do not prove that the distinct instructions or business facts can be deleted. The local timing, pair identities and provenance are retained in `.local/drafting-harness-main-20261028-v1/速度瓶颈-20261028.md`, `grouping-concurrency-code-audit.md` and `grouping-concurrency-overlap-metrics.json`; raw source wording stays local.

The same code audit identified an additional prerequisite for concurrency: `LlmProfiles` uses a plain `ThreadLocal`, so each group worker must explicitly bind the frozen model selection. A worker without that binding would fall back to the legacy local profile. The existing run-level receipt list, counters and entity persistence also assume sequential execution. Retain one coordinator for durable receipt publication and use per-call budget reservations; merely increasing the outer executor size does not solve these concerns or parallelize the loop inside a run.

The following sequence is our proposed adaptation of the workflow, context and persistence patterns above, not a recommendation to install LangGraph in the Java service. [LangGraph, Workflows and agents](https://docs.langchain.com/oss/python/langgraph/workflows-agents); [LangGraph, Checkpointers](https://docs.langchain.com/oss/python/langgraph/checkpointers)

1. **Establish the current frontend baseline.** Freeze source and graph identity, retain the raw pre-correction result, and count dispatches and manual correction work. Do not relabel a previous all-268-item run as a new grouped run.
2. **Try grouped serial work first.** Use the fixed graph to form bounded root/condition/effect groups, preserve every original source observation's coverage mapping, and reuse exact reviewed same-edition definitions. This isolates the effect of reducing task fragmentation and repeated context from the effect of concurrency.
3. **Add a bounded independent-group scheduler.** Start with two workers reading an immutable graph snapshot. Cross-group dependencies use stable read-only root IDs and run in layers, without packing the full connected graph into each request. Each worker returns proposals and its receipt. Commit results in a deterministic order with the existing revision guard and per-call budget reservation.
4. **Reuse results and evidence within their valid identity boundary.** Persist useful intermediate responses, retrieve completed receipts on resume, and invalidate only affected group inputs. Do not replay UNKNOWN dispatches automatically.
5. **Run a targeted cross-group pass only where needed.** Give it the disputed root definitions, candidate edges and supporting passages. Do not send every source and all internal bookkeeping again to an unconstrained “final integrator.” Retain provenance and unresolved states, then use the existing human group-confirmation step.

Acceptance should require no semantic or source-scope regression, a measured reduction in repeated work or elapsed time, and lower or unchanged human correction effort. Exact speed targets and the safe concurrency limit remain unmeasured on the current Qwen service. The most defensible initial gain is eliminating unnecessary re-recognition and repeated context; broader parallelization is the second experiment.
