## 最多5个容器的部署约束

2026-10-15用户明确比赛只允许5个容器。本次未说明该上限是同时运行实例、全部固定服务还是镜像总数。准备时必须区分container、Pod、image和Job；不能以5个Pod或5个阶段说明满足5容器。

当前主工程 `tools/offline_delivery/delivery.py` 的完整coordinator路径创建MySQL、Qdrant、backend、web四个CPU容器（122–149行），另加CPU coordinator（170–182行），运行任一GPU阶段时再创建一个Job容器（186–201行），峰值为6。manifest要求五类GPU stage镜像角色，但未因此证明允许额外镜像数。此为代码拓扑核对，非实际部署数量观测。

| 固定角色建议 | 职责 | 需要调整 |
| --- | --- | --- |
| 1 App | Java业务、Vue静态页面、现有文档导出能力 | 构建时将dist放入JAR静态资源或受控静态目录；取消独立web容器 |
| 2 MySQL | 业务状态、历史、恢复检查点 | 保持独立和持久化 |
| 3 Qdrant Server | 向量索引 | 保持独立和持久化 |
| 4 CPU coordinator | 请求路由、任务编排、来源/索引API及收据 | 复用现接口；严格模式将动态Job调用改为固定GPU worker协议 |
| 5 GPU执行容器 | 顺序执行Paddle、MinerU、embedding/rerank、业务LLM | 每种配方独立Python/原生环境，固定解释器和库路径；任一时刻一个GPU阶段 |

前端当前hash路由和同源`/api`便于静态合并，但现Dockerfile.backend尚未复制前端产物。若赛方只限制同时运行数，合并前端之后4CPU+1GPU可保原串行Job和按Pod释放资源的机制，改动较小。

若限制固定5容器/最多5镜像，统一GPU容器仍需实际构建和执行层改造。当前GPU worker Dockerfile只在各自NATIVE_RUNTIME_IMAGE上加入代码，并非已经合并全部环境。Paddle、MinerU、检索与LLM不能直接混装进同一pip环境；模型作为只读资产挂载，Python/原生依赖分环境固定，检查CUDA与动态库兼容。容器长期存在不等于所有模型长期驻显存。

当前`request_stage.py`依赖真实Job/Pod/PVC UID和Pod删除证据，固定worker须替换为真实worker/operation/进程所有权和持久结果契约，保SHA、超时、取消、原子发布及失败保留。现`native_provider_lifecycle._LinuxTree`可管理cgroup树，但需要平台委派可写cgroup v2和cgroup.kill，不能假定普通容器具备。若无法可靠清理完整子树，应停止后续任务并通过该GPU容器重启恢复，重新证明空闲和结果状态；不伪造Job UID或靠sleep判显存释放。

制品检查另包括：导出/上传每文件严格<50GB；容器/镜像总数核对包含临时Job、init/sidecar；替换/升级避免额外并发实例；单卡独占、冷启动、新资料和故障恢复均待实测。规则已记录，方案尚未实现、未构建或部署；模型不再调优，既有真实效果验证暂停保持。

## 是否有必要新增模型训练

默认：不把新增训练当参赛前置，赛中不默认训练业务大模型。先用现有模型完成正常链、失败归因与固定集比较；只有有证据的模型残差才进入专项训练。本结论不否定历史 OER 训练，也不把候选 loss 改善当已获得完整来源收益。

| 模型层 | 当前优先动作 | 训练候选触发条件 |
| --- | --- | --- |
| OCR/布局/表单 | 先验证 native、Paddle、MinerU、阅读规则与新整合 parser 的完整来源效果 | 跨独立来源重复的狭窄残差；完整可靠标注；独立校准/评价；小头或适配器能改善正常 parser 且保旧正确 |
| embedding/reranker | 先检查来源、切块、BM25/向量融合、候选量、排序、父条/整组闭包与预算 | query-正例-hard-negative 数据经审核；必要证据虽可得却稳定排序失败；训练收益在独立集和端到端成立 |
| 业务 LLM | 先检查实际输入、提示组织、推理与输出预算、输出契约，并比较可部署现成模型 | 给足正确材料和清晰任务仍稳定错条件、例外或引用；有高质量监督、独立留出和完整部署验证预算 |

文档生成 embedding 和索引属于预处理/推理，不是修改模型权重的训练。新合同通常先走来源登记、解析和索引。训练可以与 RAG 结合；RAFT 的研究展示了特定域的数据配方，但其基准收益不证明本项目收益，也不自动允许使用赛题/答案。[S7]

统一规格 U9 已定义最小归因：同题、同模型和受控预算，比较 A=审核完整来源+最小任务契约，B=同来源+生产 harness，C=正常 parser 产物+同 harness，D=实际 RAG 发送包+同 harness，并用固定 raw 重放接收层。A好B差先查harness，B好C差查解析，C好D差查检索/打包；A仍错才进一步比较模型和训练。层间有交互，不能把分差相减成各层错误占比。

进入训练前同时需要：

1. 赛规和数据用途允许；正式隐藏答案及评价专用资产保持隔离。
2. 明确高频错误及评分影响，非一次偶然错误或未提交材料。
3. 先完成现成工具、配方和模型的对照，训练目标足够狭窄。
4. 按项目/来源家族/近重复版本分离开发、校准、评价，teacher草稿先审核原件。
5. 固定底座、tokenizer、template、训练数据、预算和评价；导出后 fresh reload 接正常业务入口。
6. 保留基座与已采用版本；收益须含旧正确、必要条件、引用、格式、时延、资源和失败，训练失败可回退。

LoRA 通过训练较少参数降低训练成本，但仍需底座、前后向计算、激活、验证和部署工作；不能由“权重能装进显存”推导“训练能跑且值得”。训练的显存组成与推理不同，Hugging Face 官方文档对此有明确说明。[S8][S9] 本项目默认训练评估地点按已有本机边界；不能因 H800 较大便自行把训练移到赛中。
