# Unlimited OCR 2 与 ConSense OER 双解析对比调研

日期：2026-10-27（Asia/Shanghai）。结论为文献和源码调查，未运行新模型、未切换 OER 服务。

## 结论

用户进一步明确：只比较和替换 OER 中 Paddle + MinerU 承担的视觉识别及布局/表格解析部分，OER 其他阶段继续保留。Unlimited OCR 2 可作为这一视觉部分的单模型候选，若在同源原件上达到要求，可以提出删除双解析及其不再需要的专属编排；不预设必须保留双引擎。现有证据尚不足判断是否可替换或相对速度。

## 替换边界（按当前源码核对）

`原件/身份与图纸排除 → PDF 原生文字、表单及页面选择 → 页面渲染 → [双视觉解析与候选汇合] → 来源结构、覆盖与结果`。方括号才是待对照、可替换部分；页面渲染作为两边共享输入成本单独计时。原件身份、原生 PDF/Word 解析、源页与坐标映射、失败/覆盖状态、结果交付仍需要。是否改成多页请求属于候选实现的差异，须保留与物理页的映射，不应把全部 PDF 强制送入视觉模型。

当前 [complete_ocr.py](../../tools/vetting_eval/complete_ocr.py) 在缓存未命中时，对同一页依序调用 Paddle 完整 layout-parsing 与 MinerU 上传、作业、轮询和产物下载，再归一化、保存双路证据并构建整页候选；可选的行观察/补缺按条件执行。新模型应比较从相同页图输入到可供下游消费的视觉结构输出，包括实际模型加载、请求、推理、解析/坐标转换、证据保存、编排和释放；图像渲染、原生读取及其他公共阶段分开计算。双解析特有的跨引擎汇合与第二套服务开销是候选可以省去的部分，必要的来源绑定、结果验证和失败记录仍计入。单模型输出保留原始 PAGE/BLOCK、bbox、表格并正确转换到 OER 来源结构后，才能进入比较。多页方案单独计其页集合、空页和跨页映射，不与单页时间混算。

## 现有基线和职责

- [已确认规则](../oer-scope-and-rules.md)和[实施交接](../HANDOFF-ocr-embedding-rerank-20261008.md)是当前入口；[双解析架构](../adr/0002-preserve-dual-parser-evidence-and-route-by-structure.md)要求保留两路原始证据、分歧和区域/完整表格组级路由。图纸先识别身份后排除；文件中提及图纸编号的合同等仍在范围内。
- 当前比较对象应固定为 PaddleOCR-VL-1.6 完整 pipeline（含 PP-DocLayoutV3）及 MinerU 4.0.10 Standard（使用 MinerU2.5-Pro-2605-1.2B 和小模型），不是把某个同名纯文字识别模型当作完整引擎。二者均有布局、读序、表格等组件；详见[选型与版本](../vetting-layout-stack-selection-20261008.md)。
- 当前 Java 的 [DocumentParser](../../src/main/java/com/consense/document/DocumentParser.java) 有 PDF 原生文本、逐页视觉选择和覆盖/失败状态；[OcrClient](../../src/main/java/com/consense/ocr/OcrClient.java) 提供行、坐标、区域、页框、来源、覆盖和 parser evidence；[PaddleOcrClient](../../src/main/java/com/consense/ocr/PaddleOcrClient.java) 校验 wholePageGroups 中 `mineru` 和 `paddleocr-vl` 两个候选身份。新引擎不是改一个 URL 即可兼容这些契约。DOCX 仍需保留原生 POI/OOXML 的结构和修订等证据；[普通上传缺口](../testing/docx-upload-production-gap-20261022.md)不可误称已完成双视觉核对。
- 历史运行状态不能当作今日实时状态；本研究不启动 OCR，不改 DB、索引、服务或生产路由。

## 模型公开证据

[百度模型卡，固定 revision 04647c7a6098d8d58915f003536a741c82eafb40](https://huggingface.co/baidu/Unlimited-OCR-2/blob/04647c7a6098d8d58915f003536a741c82eafb40/README.md) 标注 2026-10-27 发布、MIT 许可，提供 Transformers 快测和推荐 SGLang 服务，后者依赖官方提供的定制 wheel；官方快测环境是 A800 80GB、BF16。原模型 1 的 vLLM 宣传不能直接作为 2 的支持证明。A4000 16GB 和比赛 H800 运行能力、峰值及并发均未验证。

多页示例按输入页序输出 `<PAGE>`；Transformers 多页示例为 base 全页视图，单页默认动态切片；SGLang 示例另显式设 crop mode，不能混为相同设置。官方提醒缩小页窗口可以降低显存，但可能损害跨窗口拼接。页标记存在不证明所有输出均完整且正确。

[官方原生输出及后处理说明](https://github.com/baidu/Unlimited-OCR/blob/main/utils/README.md)：原始串包含 PAGE/BLOCK、区块类型、标题级别、bbox、跨页类型和 HTML 表格，并非原生 Markdown；转换器会合并跨页块/表格、删除重复表头、清理异常标记。应保留原始生成及精确渲染和页码映射，独立验证 bbox 坐标系、页码、单元格/合并、分片完整度、跨页关联及表头是否被错误改写；不能仅保留后处理 Markdown，不能虚构置信度或行级坐标。

[百度技术报告](https://huggingface.co/baidu/Unlimited-OCR-2/blob/04647c7a6098d8d58915f003536a741c82eafb40/Unlimited-OCR-2.pdf) 第 8–12 页报告：训练伪标签来源包括 MinerU2.5-Pro 和 PaddleOCR-VL-1.6；MPDocBench（至 30 页）总体 84.59，作者新建 MarathonDocBench（100–300 页）77.06，OmniDocBench v1.6 单页 94.02。它们是作者报告的不同基准分数，不代表本项目文件上的准确率；多页表没有把本项目的两套完整 pipeline 列为直接对照，不能据此宣称优于它们。论文承认稀疏注意力不保留全局文档信息，可能限制标题层级等文档级结构。

因此可能显著改善整体速度的因素包括驻留、文件/有界页批复用、减少重复加载与传输，而这些并不自动要求更换模型。新模型自回归生成、渲染分辨率、输出长度、跨页窗口、校验和并发也会影响端到端时间；只减少解码每步成本不意味着整文档更快。

## 最小可决策的实测方案（尚未执行）

1. 离线隔离：只读选取同一份受控原件和页面，记录文件 SHA、物理页、渲染器、DPI、像素、模型 revision、依赖、精度、硬件和并发。禁止外传源文件。覆盖正文、多栏、低清扫描/隐藏文字、边框/无框表格、跨页表格、合同编号与数字、修订/脚注及限定的 APL/AoA 字段；图纸排除。
2. 对照：以相同页图和视觉结果契约比较 A 现有双解析视觉段；B 双解析驻留/有界批次候选（若可实现，作为工程优化参照）；C Unlimited OCR 2 单页动态切片；D 多页 base 与有界窗口，单列跨页片段。各自保留完整原始结果、错误、超时、漏页及实际执行数。实际运行方案和资源可用性另确认，不能预设驻留和并发已实现。
3. 原件逐页盲核关键字/金额/编号、漏字漏块、读序、表格单元格及跨页关系、位置与来源、标题层级；保留失败与不确定性。以文件级留出集检验泛化。不能用公开榜单、软件契约、生成 Markdown 或单次成功替代原件质量验收。
4. 速度分冷启动/预热、PDF 渲染、排队、推理、后处理和完整证据入库；报告整文件总耗时、实际页数、页/秒、每页分布与 P50/P95（样本数足够时）、峰值 GPU/CPU 内存、失败重试与截断，分别测 A4000 和目标 H800。对同硬件同样页与同样输出完整性比较；独立报告单模型和原有双路总成本。
5. 通过前不接入业务，不删旧引擎；如一个候选只能满足部分页面或结构，则只讨论该范围的受控路由，不宣称完全替代。原生 PDF/DOCX、来源身份、失败/部分结果和可追溯证据仍需保留。

百度[云端异步 API 文档](https://ai.baidu.com/ai-doc/OCR/Tmvp8h1l6) 是独立产品/输出契约，不能推断开源模型本地输出一致。上传原件会向外部服务发送数据；本次未调用 API、未开通服务或传送文件。
