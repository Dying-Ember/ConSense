# SL 完整单次提交：Unlimited OCR 2 在 A4000 16 GB 的容量评估

日期：2026-10-27；状态：静态源码、原件几何与资源核算，不是模型实测。用户要求先评估单次提交几千页，后续实现和对比不在本阶段预先判定通过。

## 判断

1. 官方 Transformers `infer_multi` 默认一次加载全部页图、拼出所有 base 图像张量并发送到 GPU。这条实现对于 SL 技术范围 3,174 页，单图像张量就约 18.60 GiB，加上 6.23 GiB 权重，确定不能整体放入独占的 RTX A4000 16 GB。不是实测 OOM，而是按官方固定版本执行路径及张量尺寸的下限计算。
2. 官方定制 SGLang 支持用户一次提交完整文档、服务内部按页窗口拆分、按顺序处理并拼接；这条路线理论上可以避免全部页图同时放入 GPU，但其 16 GB 峰值、几千页请求接收、总时限、完整性及质量均未实测，**不能承诺跑得起来**。用户的一次提交与内部是否分窗是两个不同问题。
3. 哪怕独占 GPU，从给定 16 GB 也不能推出 4,300 页完整源或 3,174 技术页可以在单模型上下文中同时完成。百度论文实验公开范围为 100–300 页，不能将结果直接扩展到 3,174 页。

## 输入身份与数字

当前保存的 SL 版本为 `SL2022 Batch 2 revision 1`，原件 SHA-256 `969e2a986d1a247b08fc18c39d7bed592b76fe6480a525973310a4daf46b549f`，原 PDF 4,300 物理页。现行已确认技术范围是原页 1127–4300，合计 3,174 页；初步条款范围不应因实验扩大。已对原文件计算 SHA、页数和每页 CropBox：3,165 页 200 DPI 约 1654×2339 像素，9 页约 1655×2338；按 RGB 每像素三字节加总约 34.31 GiB，指同时解压的原始像素体积估算，不是 PNG/JPEG 大小、也不是实测进程峰值。官方示例用 300 DPI，若均为同一页几何，像素内存约为 200 DPI 的 2.25 倍，属于比例估算。

官方固定 [模型 revision](https://huggingface.co/baidu/Unlimited-OCR-2/tree/04647c7a6098d8d58915f003536a741c82eafb40)：两块 BF16 safetensors 合计 6,688,305,576 bytes，即 6.23 GiB 的文件大小，不等于运行时 VRAM。RTX A4000 报告总显存 16,376 MiB，支持 compute capability 8.6。视觉编码器、attention、缓存、工作区和运行框架仍需要额外显存。

## Transformers 路线的硬边界

权重中 `modeling_unlimitedocr.py` 的 `_uocr_build_inputs` 针对每页创建 `[3,1024,1024]` 的 BF16 base 张量，`torch.stack` 合并，`_uocr_generate` 将 `imgs[1]` 送到模型所在 GPU。仅这一张量为 `3174 × 3 × 1024 × 1024 × 2 = 19,969,081,344 bytes = 18.598 GiB`；权重按文件体积加总已超过 24.8 GiB，尚未计其他内存。此下限只针对该实现、该输入模式；不能推广为定制 SGLang 的显存下限。

同一代码中 `infer_multi` 默认 `max_length=131072`，每张 base 图产生 273 个图像 token；3,174 页仅图像 token 就是 866,502，另有页标记、提示及输出。不得把缺省窗口当成能够容纳完整输入。官方 benchmark 脚本使用 786,432 的 Marathon 上下文配置，也不能直接容纳该估计的完整 base 图像 token；但 SGLang 分窗模式另有自己的窗口上下文，不能把此结果误说成 SGLang 总文档页数硬上限。

## 官方 SGLang 路线的待验证事项

固定 revision 提供的 SGLang wheel 有 `doc_split` 实现。源码 `serving_chat.py` 在兼容条件满足时以一个请求计划多个窗口；默认 `OVERLAP_PAGES=0`，相邻窗口复用前页 KV tail，可选重叠；官方示例每窗口 10 页，并预读后续页。若所有窗口上限确实为 10 且不额外受上下文限制，3,174 页理论需要 318 个窗口。相应的调度、页面重复/遗漏、KV 复用、生成预算、服务接受请求大小、客户端内存及异常恢复应实测；实际窗口数量可能不同。

wheel 的请求处理器明确将多窗口答案标为非无损，返回相关元数据；官方模型卡还说明缩小窗口会损害跨窗口拼接。论文作者也说明全局信息与文档级标题层级存在局限。因此需逐窗口核对源页号、块、跨页续文、表格和失败；不能以输出非空或 `<PAGE>` 标记数量当原件质量通过。

官方客户端示例先将 PDF 全部转为图片，将所有图片编码到一个 JSON 请求中；没有证明可以把原始 PDF 直接作为本地模型输入。请求体、base64、图片解码与 JSON 对象可能显著增加 CPU 内存；上面 34.31 GiB 是像素估算，不推导为实际 HTTP 体积或内存峰值。`max_tokens` 是全文件预算，示例为 8,000×页数；过早耗尽或 `allow-auto-truncate` 都应显式检出，不能默默算成功。一个请求内部分窗不自动具备可恢复能力；长时断连后的状态与重复页也要验证。

## 实测门槛

先准备独立的 CPU/磁盘/网络证据与固定的服务环境；在确认 GPU 可独占且不影响其他任务后，逐级测试 1 页、跨窗口页组、几十页、数百页，记录每级 VRAM 峰值、RAM、请求体大小、输入/输出 token、页数与失败。再在用户要求的完整 SL 技术范围上做单次提交，保存逐窗口终态、全量实际输出、原页和失败信息；逐项核对尾页、长表、跨窗口页、条款编号及正文。对照使用相同页图、输出契约和计时边界的当前 Paddle+MinerU，分别记录冷/热启动与总时长。任务可从原件预定范围开始，但输出质量必须人工参考原件独立判断。

模型权重下载单独留在忽略目录；本次评估未停止其他服务、没有运行新模型或基线 OCR、没有创建/切换生产分支或修改当前运行环境。
