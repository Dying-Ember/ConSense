## 这段处理在做什么

它把解析得到的原文、原件身份、段落／表格／页眉页脚位置、条件与续段等结构，保存成可追溯的来源修订。Vetting 和 Advisory 用它验证引用确实来自当前授权文件，Drafting 也消费同一普通来源图的结构上下文。内容完整、条款归属未知、人工确认状态和历史版本都必须保留；保存成功不表示来源质量或法律结论已通过。

正确顺序是上传／解析、来源准备与来源单元构建、embedding 窗口与索引、按问题检索／rerank、取回完整相关来源上下文。目前后继触发仍分散在业务服务，不能说上传已经自动完成全部索引，也不能说直到检索时才切块。

问题发生在保存和核对上述来源证据时，不是因为 embedding 需要把近十亿字符当一个窗口处理。今天的 PRE 正文为 1,491,180 UTF-16 字符，候选请求 481,512,393 B、封存 957,780,050 B；同一段落属性在完整清单、scope members、每个 part 和派生视图重复展开，另有整文字符串和字节副本。数值来源为本地 `publication13.json`、原请求和完整 CLOB 读回证据；两次桌面卡死的直接原因仍未获连续峰值证据确认，不能据这些数值单独定因。
