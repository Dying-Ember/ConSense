# External application deployment checkpoint — 29 October 2026

The requested direction is to keep frequently changed business code and released application files on persistent storage, put stable runtimes in container images, and keep model files, databases, source documents, indexes and operational evidence on persistent storage. The intended topology is an application, an OER/RAG coordinator, a GPU execution role, MySQL and Qdrant. Container, image and Job limits, platform permissions, storage behavior and security scanning rules must be verified against the actual competition environment.

## Implemented local first step

The opt-in `externalApp` mode in [offline delivery](../../tools/offline_delivery/README.md#external-application-release-opt-in) renders one backend container serving a mounted Spring Boot JAR and Vue `dist`, with MySQL, Qdrant and the existing optional CPU coordinator. The backend image contains the runtime and startup guard; JAR and frontend files are mounted from a read-only artifact volume. The exact files, SHA-256 checks and complete web file inventory are pinned in a release-specific immutable ConfigMap and checked before Java starts. A running release directory must remain immutable. Publishing a change means preparing a fresh JAR and/or frontend `dist`, complete manifest and release, then switching and checking the application; changing Java or Vue source alone does not change the running application.

With the coordinator and one serial GPU Job active, this mode renders four fixed containers plus one Job container. This is a proposed simultaneous-count topology, not proof that the platform permits it. The default mode still renders the separate web container. External routing must target the backend service on port 8080, with gateway timeouts and streaming checked independently. Configuration, source, Python code, model files, and database/index and source-evidence data have distinct lifecycles; the current coordinator and GPU images still contain Python code. The fixed GPU worker described in the proposed five-container architecture is not implemented; the existing request-bound Kubernetes Job ownership, cleanup and failure behavior remains in effect.

The pre-existing candidate requests 650 GB fast storage and 1,250 GB artifact storage. These are rendered PVC requests rather than usage measurements or confirmation of actual platform capacity. MySQL and Qdrant data must remain owned by their respective servers, with consistent backup/restore; an H2 file cannot be used as a MySQL data directory. Fixed reference indexes must remain bound to the correct originals, parser outputs, model and index identities. Credentials do not belong in the source tree or release manifest.

## Evidence and remaining work

The deployment renderer and startup-guard tests exercise authored fixtures and reject changed or extra files. A separate local smoke using an older Windows JAR, isolated H2 in-memory database, disabled LLM/OCR, in-memory vector store and a task-owned port returned the expected external index, static asset and API responses; its receipt and JAR hash are retained under `.local/static-http-6c55aa4a891a40b3b2408ac8b9aa85b0/`. This establishes only the observed old-JAR mechanism, not the current source tree, a container image, or business acceptance.

A subsequent native Linux smoke used the freshly packaged candidate JAR (`fd4a3a8404c1380cc43f03cbe0fa2a05a944242d38d0cfd792c2de4ba1928154`) and the separately built frontend. It invoked the actual external-app entrypoint and SHA inventory, then verified `/`, one JavaScript asset and `/api/system/llm-profiles` on a task-owned loopback port with in-memory H2 and vector storage and model/OCR disabled. The receipt is `.local/merge-deployment-20261029/external-app-final-smoke.json`; the owned process was stopped. This checks the native-process path, not a built container, the target platform or application business results.

The following remain open: externalizing coordinator/worker business code with pinned release identity; implementing and proving a fixed GPU worker if the platform does not permit sequential Jobs; offline Linux runtime/image construction; complete model, font and native-dependency inventories; MySQL and Qdrant migration and recovery; exact external gateway, storage, permissions and scanner requirements; and actual new-source OCR, retrieval, model, browser, export and H800 acceptance. File uploads must comply with the competition notice's per-file limit and scanning process; split-file or image-count permissions are not assumed. Do not infer model quality, original-source quality or business acceptance from source, fixture tests, HTTP readiness or the old-JAR smoke.
